# 角色类提示词目录（roles）

> 本目录是 easy-web-tab 项目中**角色设定类提示词**的唯一存放位置。
> 目录结构与书写格式沿用 `public/skills/`（`SKILL.md` 体系）的既有约定，便于同一套工具与心智模型维护。

---

## 一、适用范围

**只收纳「角色设定类」提示词**：即让 AI **扮演某个固定身份**去完成工作的提示词。判定标准是它必须同时具备下面四要素：

| 要素 | 作用 | 缺了会怎样 |
|---|---|---|
| 角色背景 | 说明「你是谁、资历如何、擅长什么」 | AI 不知道以什么水平作答 |
| 语气风格 | 说明「怎么说」：口吻、篇幅、术语密度 | 输出忽长忽短、风格漂移 |
| 行为边界 | 说明「能做什么、不能做什么、不确定时怎么办」 | 越权臆造、该拒答时不拒答 |
| 输出格式 | 说明「以什么结构交付」：章节、表格、清单 | 每次结构都不一样，难以直接使用 |

**不属于本目录、请勿混入的内容**：

- 一次性任务指令（如「把这封邮件改写得礼貌些」）→ 属于普通提示词，不设固定角色
- 操作流程 / 工具用法指南（如「如何新增一个工作台面板」）→ 属于技能，放 `public/skills/<name>/SKILL.md`
- 项目规范、需求文档、接口说明 → 放 `docs/`
- 代码模板、可执行脚本 → 放对应代码目录

一句话判据：**能回答「它让 AI 扮演谁」的，才是角色类提示词。**

---

## 二、目录结构与命名

沿用 `public/skills/` 的约定：

```
public/prompts/roles/
├── README.md              ← 本说明（目录内唯一不带 frontmatter 的文件）
├── code-reviewer.md       ← 角色提示词：小写连字符 + .md
└── requirement-analyst.md
```

- **目录名**：小写英文、连字符分词（与 `public/skills/easy-webtab-backup-editor/` 一致）
- **文件名**：小写连字符 + `.md`，以「角色身份」命名（如 `code-reviewer.md`），**不要**用 `ROLE.md` / `SKILL.md`
- **一文件一角色**：一个角色一个文件，不把多个角色塞进同一个文件

> 与 `public/skills/` 的差异只有一处：那边是**技能**（文件固定叫 `SKILL.md`，遵循 Agent Skills 规范），
> 这边是**角色提示词**（文件名即角色名），所以文件用小写 `.md`。

## 三、书写格式

### 3.1 frontmatter（必写）

与 `public/skills/SKILL.md` 完全一致的 YAML frontmatter，只写两个键，值用双引号包裹：

```yaml
---
name: "代码评审官"
description: "以资深评审官身份审查代码改动。当需要他人对一段 Vue 3 / TypeScript 代码给出结构化、可执行的改进建议时使用。覆盖正确性、可读性、性能、安全与可维护性，最后给出必须改 / 建议改两档清单。"
---
```

| 键 | 是否必需 | 写法要求 |
|---|---|---|
| `name` | **必需** | 角色名，2–8 字，中文优先；库内唯一，也是智能工作台里的显示标题 |
| `description` | **必需** | **一句话**说明「做什么 + 什么时候该用它」，必须包含触发场景，否则无法判断何时调用 |

`description` 的推荐句式：`以……身份……。当需要……时使用。覆盖……，最后……。`

### 3.2 正文结构（四要素缺一不可）

正文用 Markdown，章节编号沿用项目既有的中文数字序号（`## 一、` `## 二、`…）：

```markdown
# 角色：<角色名>

## 一、角色背景
## 二、语气风格
## 三、行为边界
## 四、输出格式
## 五、使用示例（可选）
```

- **角色背景**：身份、年限、擅长领域、默认技术栈
- **语气风格**：口吻（直给 / 温和）、篇幅、是否用术语、是否给结论先行
- **行为边界**：分「会做 / 不会做 / 遇到 X 怎么办」三类写，**必须写明不确定时的处理**（追问而不是编造）
- **输出格式**：给出可直接照抄的 Markdown 骨架，含具体章节名与表格列
- 需要用户填内容时用 `{{变量名}}` 占位（与智能工作台提示词的变量语法一致）

### 3.3 自检清单

提交前逐项确认：

- [ ] frontmatter 的 `name` / `description` 齐全，且 `description` 写清了触发场景
- [ ] 正文四要素齐全，没有混入操作流程类内容
- [ ] 「行为边界」里写明了不确定时如何处理
- [ ] 「输出格式」是可直接套用的结构，而不是一句「请你输出清晰一点」
- [ ] 已在「四、注册与生效」列出的文件中完成同步

## 四、注册与生效

新增一个角色文件后，要在**两处**同步才能被正常加载使用：

| # | 文件 | 做什么 | 不做的后果 |
|---|---|---|---|
| 1 | `src/composables/smartCore.ts` → `BUILT_IN_PROMPTS` | 追加一条：`category: '角色'`，`title` 与 frontmatter 的 `name` 一致，`content` 取文件正文主干（可省略末尾「使用示例」章节） | 智能工作台的提示词库里看不到该角色（分类下拉与列表都由数据派生，没有这份数据就不会出现） |
| 2 | `public/prompts/roles/<name>.md` | 本目录下的源文件（本文件） | 项目里没有可分发 / 可版本管理的角色原文 |

**生效时机**：`BUILT_IN_PROMPTS` 只在两种情况下写入库——
① 首次进入且技能库与提示词库**都为空**时自动播种；
② 用户点提示词页的「恢复内置示例」（`store.restoreBuiltIns()`，按 id 幂等补回）。
所以已经用了一段时间的库，新增角色后需要点一次「恢复内置示例」才会出现，这是预期行为，不是 Bug。

**无需改动**的地方（避免重复劳动）：

- `src/stores/smart.ts` —— 播种与「恢复内置示例」直接读 `BUILT_IN_PROMPTS`，自动生效
- `src/components/smart/PromptManager.vue` —— 分类下拉来自 `store.promptCategories`，由数据派生，新增条目带 `category: '角色'` 后自动出现
- `vite.config.js` —— `public/` 下文件在构建时自动复制到 `dist/`，无需登记

如果还要让角色提示词在**帮助弹窗**中可被下载（像 `easy-webtab-backup-editor.zip` 那样），
需额外在 `src/components/HelpModal.vue` 中加一个 `fetch('/prompts/roles/...')` 入口 —— 当前未启用，按需添加。
