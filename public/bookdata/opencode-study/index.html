#🚀 快速开始

#1. 安装 OpenCode

# 官方安装脚本（推荐）
curl -fsSL https://opencode.ai/install | bash

# 或使用 npm
npm install -g opencode-ai

# 或使用包管理器
brew install anomalyco/tap/opencode   # macOS/Linux
choco install opencode                # Windows
scoop install opencode                # Windows

#OpenCode 配置详解

#一、配置文件格式

OpenCode 的配置就像手机里的"设置页"：改一行，行为就变。好在它支持 JSON 和 JSONC（带注释的 JSON）两种格式，写起来很直观——JSONC 允许你在配置里写注释，方便记下"这一条为什么这么设"。

#基本示例

{
  "$schema": "https://opencode.ai/config.json",
  "model": "anthropic/claude-sonnet-4-5",
  "autoupdate": true
}

#二、配置文件位置

配置文件会合并加载，后加载的会覆盖先加载的（仅冲突键）。

把这套机制想象成先铺底色、再叠图层的绘画过程：全局配置是画布上铺好的底色，项目配置是盖在上面的局部图层。图层叠得越靠上、越具体，颜色就越鲜亮——后加载的配置赢。而且它只覆盖"冲突"的键：底层没被盖住的地方，依然透出原来的颜色。

举个例子：你在全局配置里设了 "model": "A"，项目配置里设了 "model": "B"，最终生效的是 B（后加载的赢了）；但如果你只在全局配置里开了 "autoupdate": true，项目配置完全没提它，这个值就原样保留，不会被抹掉。

#加载优先级（从低到高）

优先级位置说明

#推荐配置方式

全局配置（用户级）：

~/.config/opencode/opencode.json

项目配置（项目级）：

your-project/opencode.json
💡 小贴士： 养成一个好习惯——"共同偏好"放全局，"项目专属"放项目。比如把默认模型、快捷键放全局，把项目的 instructions、依赖目录放项目配置，两边各司其职，换项目也不用重配。

#三、核心配置项

下面这些是出场率最高的配置项。原文逐条看之前，先记住一个原则：没写的就是默认值，写了才生效。

#1. 模型配置

{
  "$schema": "https://opencode.ai/config.json",
  "model": "anthropic/claude-sonnet-4-5",
  "small_model": "anthropic/claude-haiku-4-5"
}
字段说明
model主模型，用于复杂任务
small_model轻量模型，用于标题生成等简单任务

类比： model 是主力干将，负责攻坚克难；small_model 是跑腿小弟，专门处理标题生成这类杂活——快、便宜、杀鸡不用牛刀。

#2. 提供商配置

{
  "$schema": "https://opencode.ai/config.json",
  "provider": {
    "anthropic": {
      "options": {
        "timeout": 600000,
        "chunkTimeout": 30000
      }
    }
  }
}

可用选项：

  • timeout - 请求超时（毫秒），默认 300000，设为 false 可禁用
  • chunkTimeout - 流式响应块超时（毫秒）
  • setCacheKey - 确保始终设置缓存密钥
  • baseURL - 自定义 API 端点
  • blacklist / whitelist - 过滤模型列表
⚠️ 常见坑： 长对话偶尔"卡住"、报超时错误，十有八九是 timeout 太短。跑大文件、长任务时，可以像示例那样把超时调大一点。

#3. 服务器配置

{
  "$schema": "https://opencode.ai/config.json",
  "server": {
    "port": 4096,
    "hostname": "0.0.0.0",
    "mdns": true,
    "mdnsDomain": "myproject.local",
    "cors": ["http://localhost:5173"]
  }
}
字段说明
port监听端口
hostname监听主机
mdns启用 mDNS 服务发现
mdnsDomain自定义 mDNS 域名
cors额外的 CORS 来源

#4. Shell 配置

{
  "$schema": "https://opencode.ai/config.json",
  "shell": "pwsh"
}

Windows 下可设为 pwsh（PowerShell）或 cmd.exe。

小贴士： 如果你在 Windows 上用 PowerShell，设成 pwsh 能让 AI 执行的命令行为与你的日常终端保持一致，减少"能跑和不能跑"的错位。

#5. 权限配置

{
  "$schema": "https://opencode.ai/config.json",
  "permission": {
    "edit": "ask",
    "bash": "ask",
    "write": "allow",
    "read": "allow"
  }
}

权限值：

把这三个值想成小区门禁的三种状态：

  • "allow" - 允许执行（绿名单，直接放行，不用按门铃）
  • "deny" - 禁止执行（黑名单，来了就拦，连问都不问）
  • "ask" - 需要用户确认（访客登记，每次都要先问你要不要放行）

上面这份配置的翻译是：让 AI 读文件、写文件随便来（allow），但改代码、跑命令之前都要先问你一声（ask）。

#6. 权限配置（细粒度）

{
  "$schema": "https://opencode.ai/config.json",
  "permission": {
    "*": "ask",
    "bash": {
      "*": "ask",
      "git status*": "allow",
      "git push*": "deny"
    },
    "edit": "allow",
    "read": "allow"
  }
}

权限值：（同前）"allow" 允许执行，"deny" 禁止执行，"ask" 需要用户确认。

可用权限字段：

  • read - 读取文件
  • edit - 文件修改（覆盖 edit、write、apply_patch）
  • glob - 文件搜索
  • grep - 内容搜索
  • bash - shell 命令
  • task - 启动子 Agent
  • skill - 加载技能
  • lsp - 语言服务器
  • question - 向用户提问
  • webfetch - 网页抓取
  • websearch - 网络搜索
  • external_directory - 外部目录访问
  • doom_loop - 循环检测恢复
注意： bash、edit、read 等支持对象语法进行细粒度控制，最后匹配的规则生效。
💡 小贴士： 上面这份配置是"大门敞开、小门把关"的思路：默认所有操作都要问（"*": "ask"），但 git status* 这类无害查询直接放行，git push* 这类危险操作彻底拦死，改代码和读文件则完全放开。

#7. 工具配置（已废弃）

{
  "$schema": "https://opencode.ai/config.json",
  "tools": {
    "write": false,
    "bash": false
  }
}
注意： tools 配置已废弃，请改用 permission 字段。

#六、上下文压缩

当对话过长时，自动压缩上下文：

{
  "$schema": "https://opencode.ai/config.json",
  "compaction": {
    "auto": true,
    "prune": false,
    "reserved": 10000
  }
}
字段说明
auto上下文满时自动压缩
prune删除旧工具输出以节省 token
reserved压缩时保留的 token 缓冲区

类比： 上下文压缩就像收拾行李箱——装不下了，就把不重要的旧衣服（旧工具输出）压一压、卷一卷，给贵重物品（当前任务的关键信息）留出空间（reserved）。开了 prune 等于允许直接扔掉一些旧东西，更省地方，但丢了就找不回来了。

#七、指令文件

可以指定额外的指令文件来指导 AI：

#十一、调试配置

配置生效没生效、被谁覆盖了，肉眼很难看清。运行以下命令查看最终配置：

小贴士： 遇到"我明明配了怎么不生效"的玄学问题，先跑这条命令——它会打印合并后的最终配置，一眼就能看出是不是被某个更高优先级的配置覆盖了。

#本章小结

  • 配置分 JSON / JSONC 两种格式，JSONC 支持写注释。
  • 配置按优先级合并加载：后加载的赢，且只覆盖冲突键（先铺底色、再叠图层）。

  • 权限值是门禁三态：allow 直接放行、deny 拦死、ask 每次询问。
  • 拿不准配置对不对，用 opencode debug config 看最终结果。

#OpenCode 工具使用指南

#一、概述

想象 OpenCode 是一位背着工具箱的工程师：你描述需求，他打开工具箱挑趁手的家伙——要改一行代码，抄起手术刀；要新建整个文件，翻开整页纸重写；要搜项目里某个字符串，拿起放大镜。这套工具让 AI 可以直接操作你的代码库。所有工具默认启用且无需审批，可通过权限配置控制。

💡 记住一句话： 工具本身不可怕，可怕的是不给它们装"门禁"。看完这一篇，你会知道每件工具什么时候该用、什么时候要拦着。

#二、内置工具一览

工具用途权限字段
bash执行终端命令bash
edit精确修改文件edit
write创建/覆写文件edit
read读取文件内容read
grep正则搜索文件内容grep
glob通配符搜索文件名glob
list列出目录内容read
apply_patch应用补丁edit
skill加载技能文件skill
todowrite管理任务列表todowrite
task启动子 Agenttask
webfetch抓取网页内容webfetch
websearch搜索网络websearch
question向用户提问question
lsp语言服务器交互（实验性）lsp
注意： edit、write、apply_patch 三个工具共用 edit 权限。

把这一点讲透： 这三个是"改文件三兄弟"——edit 是精准手术刀（改一处），write 是整页重写（新建/覆盖），apply_patch 是批量贴补丁（应用 diff）。虽然各有分工，但门口登记用的是同一张通行卡 edit。你把 edit 设为 ask，三兄弟每次动手都会先问你；设为 deny，三个全部罢工。反过来，想"只准读、彻底禁止改"，把 edit 设成 deny 就够了，不用一个一个去拦。

#三、各工具详解

#1. bash - 执行终端命令

运行任意 shell 命令，如构建、测试、Git 操作等。它是工具箱里功能最强、也最危险的一件——因为终端里几乎什么都能干。

使用场景：

  • 运行 Maven/Gradle 构建
  • 执行 Git 命令
  • 运行测试
  • 安装依赖

示例：

mvn clean install
git status
git log --oneline -10
java -version

什么时候用： 构建、测试、跑 Git 流程、装依赖这类"非它不可"的操作。 什么时候别用： 只是想看一眼文件内容——用 read 更安全更快；想精确改代码——别让 AI 用 sed 硬改，用 edit 更不容易出错。

权限配置：

{
  "permission": {
    "bash": "ask"
  }
}

细粒度控制：

{
  "permission": {
    "bash": {
      "*": "ask",
      "git status*": "allow",
      "git push*": "deny"
    }
  }
}
💡 小贴士： 这套规则就像小区门口的保安：git status* 这类只读查询在放行清单上，直接过；git push* 这类危险动作在黑名单里，拦死；其余命令都得先问过你。详见下文「权限管理」。

#2. edit - 精确修改文件

通过精确字符串匹配来修改文件内容，是最主要的代码修改方式。

使用场景：

  • 修改函数实现
  • 更改变量名
  • 调整代码逻辑
  • 修复 Bug

工作原理：

  1. 找到文件中的精确文本
  2. 替换为新内容
  3. 确保只修改目标位置

什么时候用： 改文件里的某一处、某几处——手术刀式的小改动。 什么时候别用： 想整个文件推倒重写——用 write 更省事；想批量改很多相似的地方——考虑 apply_patch。

#3. write - 创建/覆写文件

创建新文件或完全覆写现有文件。

使用场景：

  • 创建新类/接口
  • 生成配置文件
  • 重写整个文件

什么时候用： 建新文件、生成配置、整体重写。 什么时候别用： 大文件里只改中间几行——用 write 会把整个文件重写一遍，浪费 token 还容易手滑，用 edit 更精准。

注意： 受 edit 权限控制，不是独立权限。

#4. read - 读取文件

读取文件内容，支持指定行号范围。

使用场景：

  • 查看代码实现
  • 分析文件结构
  • 阅读配置文件

支持大文件： 可通过 offset 和 limit 读取特定部分。

什么时候用： 看代码、读配置、了解某个文件的实现细节。 什么时候别用： 在成百上千个文件里找某个字符串——用 grep；只想确认某类文件名——用 glob 更快。

注意： .env 文件默认被拒绝读取，需要显式允许。
⚠️ 常见坑： 别指望 AI 能直接读到 .env 里的密钥——这是默认拦死的，属于安全设计，不是 bug。

#5. grep - 正则搜索

使用正则表达式搜索文件内容，底层使用 ripgrep。这是"内容大海捞针"的专用工具。

使用场景：

  • 查找特定函数调用
  • 搜索错误信息
  • 定位代码模式

示例：

搜索所有 TODO 注释：TODO
搜索 Spring 注解：@Service|@Repository|@Controller
搜索特定方法调用：\.findAll\(

文件过滤：

只搜索 Java 文件：pattern="UserService" include="*.java"

特性： 自动遵守 .gitignore 规则。

什么时候用： 按内容找代码——搜报错信息、找调用点、定位模式。 什么时候别用： 按文件名找——那是 glob 的活；搜索前可先用 glob 圈定范围，让 grep 更快更准。

#6. glob - 文件搜索

使用通配符模式搜索文件名。

使用场景：

  • 查找特定类型的文件
  • 定位项目结构
  • 发现配置文件

示例：

查找所有 Java 文件：**/*.java
查找 Controller：**/*Controller.java
查找配置文件：**/application*.yml

什么时候用： 按文件名/路径找文件、摸清项目结构。 什么时候别用： 想在文件内容里搜——那是 grep 的活。

#7. list - 列出目录

列出目录中的文件和子目录。

使用场景：

  • 浏览项目结构
  • 查看特定目录下的文件

什么时候用： 快速扫一眼某个目录里有什么。 什么时候别用： 需要精确搜索时——glob/grep 直接命中目标，比一层层 list 翻目录高效得多。

#8. apply_patch - 应用补丁

应用 diff 补丁到文件，适合批量修改。

使用场景：

  • 应用 Git diff
  • 批量重构
  • 应用代码审查建议

补丁格式示例：

*** Add File: src/main/java/com/example/NewService.java
--- /dev/null
+++ b/src/main/java/com/example/NewService.java
@@ -0,0 +1,20 @@
+package com.example;
+
+public class NewService {
+    // ...
+}

*** Update File: src/main/java/com/example/ExistingService.java
--- a/src/main/java/com/example/ExistingService.java
+++ b/src/main/java/com/example/ExistingService.java
@@ -10,7 +10,7 @@
-    old code
+    new code

什么时候用： 手里已有一份 diff（比如 review 建议、Git diff），要一次性落到多个文件。 什么时候别用： 只是单点小改动——edit 更直观，报错也更好理解。

#9. skill - 加载技能

加载 SKILL.md 文件，获取特定任务的指导。

使用场景：

  • 加载项目特定的工作流
  • 获取编码规范指导
  • 执行复杂任务流程

技能文件位于 .opencode/skills/<名称>/SKILL.md 或 ~/.config/opencode/skills/<名称>/SKILL.md。

什么时候用： 有既定流程要照章办事——比如"按公司规范发版""按项目模板生成代码"。 什么时候别用： 临时随口一问的小问题——直接对话即可，不必动用技能文件。

#10. todowrite - 任务管理

创建和管理待办事项列表，跟踪复杂任务进度。

使用场景：

  • 多步骤任务分解
  • 进度跟踪
  • 任务状态管理

状态：

  • pending - 待处理
  • in_progress - 进行中
  • completed - 已完成
  • cancelled - 已取消

什么时候用： 多步骤、跨文件的大任务——列个清单，AI 不容易做着做着忘事。 什么时候别用： 一句话就能说清的小改动——不值得建清单。

注意： 子 Agent 默认禁用此工具，需要手动启用。

#11. task - 启动子 Agent

启动一个子 Agent 来处理复杂的多步骤任务。

使用场景：

  • 并行执行多个独立任务
  • 需要专门化的 Agent 处理特定问题
  • 复杂的搜索和研究任务

可用的内置子 Agent：

  • general - 通用子 Agent，适合复杂搜索和多步骤任务
  • explore - 只读探索，快速搜索代码库
  • scout - 外部文档和依赖研究

使用方式： 在消息中用 @ 提及子 Agent：

@general 帮我搜索所有使用了这个函数的地方
@explore 找出项目中的所有 API 端点

什么时候用： 任务独立、量大、适合并行——派几个"实习生"分头干，最后汇总。 什么时候别用： 一两步就能搞定的改动——启动子 Agent 有额外开销，杀鸡不用牛刀。

#12. webfetch - 网页抓取

获取指定 URL 的内容。

使用场景：

  • 查阅官方文档
  • 获取 API 文档
  • 研究技术方案

示例：

帮我查阅 Spring Boot 文档：https://spring.io/docs
查看这个 GitHub Issue：https://github.com/xxx/issues/123

什么时候用： 已经知道确切 URL，要把它拿下来读（检索）。 什么时候别用： 不知道 URL、要"找"资料——先用 websearch 搜，搜到 URL 再 fetch。

#13. websearch - 网络搜索

使用 Exa AI 搜索网络信息。

使用场景：

  • 搜索技术方案
  • 查找最新资讯
  • 研究问题解决方案

启用条件：

OPENCODE_ENABLE_EXA=1 opencode

或使用 OpenCode 提供商。无需 API 密钥。

什么时候用： 没头绪、要"找"信息——搜关键词、看结果（发现）。 什么时候别用： 已有明确的 URL——直接 webfetch 更快，省一次搜索往返。

提示： 用 websearch 搜索信息（发现），用 webfetch 获取特定 URL 的内容（检索）。

#14. question - 向用户提问

在执行过程中向用户确认或询问。

使用场景：

  • 收集用户偏好
  • 确认实现方案
  • 解决歧义

每个问题包含标题、问题文本和选项列表。用户可以选择或输入自定义答案。

什么时候用： 需求有歧义、方向需要拍板——AI 停下来问清楚，好过闷头干错。 什么时候别用： 答案显而易见、能合理推断时——来回问答反而打断节奏。

#15. lsp - 语言服务器（实验性）

与配置的 LSP 服务器交互，获取代码智能功能。

启用方式：

OPENCODE_EXPERIMENTAL_LSP_TOOL=true opencode

支持的操作：

  • goToDefinition - 跳转到定义
  • findReferences - 查找引用
  • hover - 悬停信息
  • documentSymbol - 文档符号
  • workspaceSymbol - 工作区符号
  • goToImplementation - 跳转到实现
  • prepareCallHierarchy - 调用层次
  • incomingCalls / outgoingCalls - 调用关系

什么时候用： 需要精确的代码智能——"这个类被谁引用""这个方法的实现跳去哪"。 什么时候别用： 需要整体上下文理解——LSP 给你的是"点状"信息，宏观问题直接问 AI 更合适。

#四、权限管理

前面讲了工具，这一节讲门禁——给每件工具定规矩。

#权限级别

{
  "permission": {
    "工具名": "allow | deny | ask"
  }
}
值行为
allow直接执行，不询问
deny禁止执行
ask执行前询问用户

#全局通配符

控制所有工具的默认权限：

{
  "permission": {
    "*": "ask",
    "bash": "allow"
  }
}

解读： 先把大门设成"访客登记"（* 为 ask），再给 bash 单独发一张绿卡（allow）——想放行的逐个开绿灯。

#细粒度控制（对象语法）

对 bash、edit、read 等工具，可以用对象语法按输入内容分别控制：

{
  "permission": {
    "bash": {
      "*": "ask",
      "git status*": "allow",
      "git push*": "deny",
      "grep *": "allow"
    }
  }
}

规则匹配： 最后匹配的规则生效。把 * 放前面，具体规则放后面。

保安类比： 这就像给保安一份"放行手册"——git status*（看看状态）直接放行，git push*（推代码上远端）当场拦死，grep *（搜东西）也放行，其余统统"先问我"。注意规则的先后顺序：* 是兜底，写在最前面；越具体的规则放越后面，因为最后匹配的才生效。

#MCP 工具控制

用通配符控制某个 MCP 服务器的所有工具：

{
  "permission": {
    "mymcp_*": "ask"
  }
}

#外部目录访问

默认情况下，访问项目工作目录之外的路径需要授权：

{
  "permission": {
    "external_directory": {
      "~/projects/personal/**": "allow"
    }
  }
}

#Auto 模式

启动时加 --auto 可自动批准非拒绝的权限请求：

opencode --auto
opencode run --auto "重构这个模块"
⚠️ 常见坑： --auto 确实省事，但也等于把门禁钥匙全交给 AI。建议只在可信的、你熟悉的项目里用，团队共享的仓库慎开。

#推荐配置

开发模式（宽松）：

{
  "permission": {
    "edit": "allow",
    "bash": "allow",
    "read": "allow"
  }
}

安全模式（严格）：

#OpenCode 模型提供商指南

想象一下：家里墙上只有一个插座，却要同时伺候手机、平板、笔记本和充电宝，而且每个设备的充电口还不一样。你不需要换插座——只要备好几根转接线，一个插座就能通吃所有设备。
OpenCode 也是这个思路。它通过 AI SDK 和 Models.dev 把 75+ 家模型提供商 统一「接到」同一个终端里：无论你偏爱 Claude、GPT，还是想用国产大模型，只要 /connect 连上对应提供商，就像插上对应的充电线，马上通电开工。这一章就带你把这些「插头」认全、接对。

#六、本地模型

场景：周末坐高铁回老家，一路穿过隧道，手机信号时有时无，可你答应了同事周一交代码。这时候云端模型全线罢工，怎么办？
答案：本地模型。把模型下载到你的电脑上，OpenCode 直接调用本机推理服务，断网也能干活。代价是本地模型的「脑子」比云端小一号，复杂任务力不从心，但改 bug、写测试、重构这类常规编码活完全够用。

#Ollama

最适合入门本地模型的选择——安装简单，一条命令就能拉起服务。

安装： 访问 https://ollama.com/

配置：

{
  "$schema": "https://opencode.ai/config.json",
  "provider": {
    "ollama": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "Ollama (local)",
      "options": {
        "baseURL": "http://localhost:11434/v1"
      },
      "models": {
        "llama2": {
          "name": "Llama 2"
        },
        "qwen3-coder": {
          "name": "Qwen3 Coder"
        }
      }
    }
  }
}

提示： 如果工具调用不工作，尝试在 Ollama 中增加 num_ctx（16k-32k）。

#OpenCode 高级功能

上一章解决了「用哪个模型」的问题，这一章解决「AI 有多懂你」。把这章的功能用起来之后，AI 就不再是一个只会聊天的「实习生」，而是一个读过项目手册、自带工具箱、连得上公司数据库的资深同事。

#一、Rules（规则）

#什么是 Rules？

Rules 用于定义项目级的行为规则，指导 AI 如何在你的项目中工作。OpenCode 支持多种方式定义规则。

把 Rules 想成 「给 AI 的项目说明书」：新同事入职第一天，你会递给他一本手册——项目是干什么的、用什么技术栈、代码该怎么写、构建测试命令是什么。AI 每次开始新会话都像「第一天入职」，Rules 就是提前交给它的那本手册，让它不用反复问东问西，也不会答非所问。

#AGENTS.md

运行 /init 会自动分析项目并创建 AGENTS.md 文件。这是最简单的规则方式——相当于让 AI 自己先写一版「说明书初稿」，你再手动补充完善。

以 Spring Boot 项目为例，看看这份说明书是怎么给 AI 指路的：

# AGENTS.md

## 项目概述
这是一个 Spring Boot 微服务项目。

## 技术栈
- Java 17
- Spring Boot 3.2
- MyBatis Plus
- MySQL 8.0

## 编码规范
- 使用 Lombok 简化代码
- 异常统一使用 GlobalExceptionHandler 处理
- 所有 API 返回统一的 Result 包装类

## 常用命令
- 构建：`mvn clean install`
- 测试：`mvn test`
- 单个测试：`mvn test -Dtest=UserServiceTest`

逐段翻译一下这份「说明书」：

  • 项目概述 + 技术栈：告诉 AI「你面对的是什么」，它就不会用 Node 的思维去改 Java 代码；
  • 编码规范：AI 生成的代码默认符合团队规矩——用 Lombok、异常统一走 GlobalExceptionHandler、响应包一层 Result，省得你逐条 review；
  • 常用命令：AI 想验证改动时，会直接跑 mvn test 而不是瞎猜命令。
💡 小贴士：说明书越具体，AI 越省心。把编码规范、部署方式、代码风格都写进去，效果立竿见影。

#instructions 配置

除了 AGENTS.md，还可以在 opencode.json 中指定额外的规则文件，把贡献指南、团队文档也纳入 AI 的视野：

{
  "$schema": "https://opencode.ai/config.json",
  "instructions": [
    "CONTRIBUTING.md",
    "docs/guidelines.md",
    ".cursor/rules/*.md"
  ]
}

支持 glob 模式。这些文件的内容会作为上下文提供给 AI。

#二、Custom Tools（自定义工具）

#什么是自定义工具？

自定义工具让你创建 LLM 可以调用的函数，用 TypeScript/JavaScript 定义，但可以调用任意语言的脚本。

AI 的「手」是有限的——它能读文件、改代码，但查不了你们公司的数据库、调不了内部接口。自定义工具就是给 AI 装上的「专业手套」：你定义好函数，AI 在需要的时候自己去调用。

#创建工具

在 .opencode/tools/ 或 ~/.config/opencode/tools/ 目录下创建 .ts 或 .js 文件：

// .opencode/tools/database.ts
import { tool } from "@opencode-ai/plugin"

export default tool({
  description: "查询项目数据库",
  args: {
    query: tool.schema.string().describe("SQL 查询语句"),
  },
  async execute(args, context) {
    const { agent, sessionID, directory, worktree } = context
    // 你的数据库逻辑
    return `执行查询: ${args.query}`
  },
})

文件名即工具名。 上面创建了一个 database 工具。

#多个工具导出

一个文件可以导出多个工具，名称格式为 <文件名>_<导出名>：

// .opencode/tools/math.ts
import { tool } from "@opencode-ai/plugin"

export const add = tool({
  description: "两数相加",
  args: {
    a: tool.schema.number().describe("第一个数"),
    b: tool.schema.number().describe("第二个数"),
  },
  async execute(args) {
    return (args.a + args.b).toString()
  },
})

export const multiply = tool({
  description: "两数相乘",
  args: {
    a: tool.schema.number().describe("第一个数"),
    b: tool.schema.number().describe("第二个数"),
  },
  async execute(args) {
    return (args.a * args.b).toString()
  },
})

这会创建 math_add 和 math_multiply 两个工具。

#调用其他语言

工具定义用 TypeScript，但可以调用任意语言的脚本——TypeScript 只是「外壳」，真正干活儿的可以是 Python、Shell 或任何你熟悉的语言：

# .opencode/tools/add.py
import sys
a = int(sys.argv[1])
b = int(sys.argv[2])
print(a + b)
// .opencode/tools/python-add.ts
import { tool } from "@opencode-ai/plugin"
import path from "path"

export default tool({
  description: "用 Python 两数相加",
  args: {
    a: tool.schema.number().describe("第一个数"),
    b: tool.schema.number().describe("第二个数"),
  },
  async execute(args, context) {
    const script = path.join(context.worktree, ".opencode/tools/add.py")
    const result = await Bun.$`python3 ${script} ${args.a} ${args.b}`.text()
    return result.trim()
  },
})
什么时候值得用： 当项目里有「只有团队内部才懂的操作」时——查公司数据库、调内部 API、跑私有脚本。如果只是让 AI 读写文件、改改代码，用不上自定义工具。

#三、MCP Servers（模型上下文协议）

#什么是 MCP？

MCP（Model Context Protocol）允许集成外部工具和服务。

把它想成 「给 AI 接 USB 外设」：电脑机身只有一个 USB 口，但插上打印机就能打印、插上 U 盘就能拷文件、插上摄像头就能开会。MCP 就是 AI 的「USB 口」——通过一套标准协议，把数据库、GitHub、文件系统等外部服务「插」给 AI。两种插法：

  • 本地 MCP（local）：外设插在本机，通过 stdio 启动子进程通信；
  • 远程 MCP（remote）：外设放在云端，通过 HTTP/SSE 远程连接。

#配置示例

下面的配置一次接了两个「外设」——本地数据库和远程 GitHub：

{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "database": {
      "type": "local",
      "command": ["npx", "-y", "@modelcontextprotocol/server-postgres", "postgresql://localhost:5432/mydb"],
      "environment": {
        "NODE_ENV": "production"
      }
    },
    "github": {
      "type": "remote",
      "url": "https://github.com/mcp"
    }
  }
}

#本地 MCP 服务器

{
  "mcp": {
    "my-server": {
      "type": "local",
      "command": ["node", "./my-mcp-server.js"],
      "environment": {
        "API_KEY": "xxx"
      }
    }
  }
}

#远程 MCP 服务器

{
  "mcp": {
    "remote-service": {
      "type": "remote",
      "url": "https://api.example.com/mcp"
    }
  }
}

#完整配置示例

{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "filesystem": {
      "type": "local",
      "command": ["npx", "-y", "@modelcontextprotocol/server-filesystem", "/path/to/allowed/directory"],
      "environment": {
        "NODE_ENV": "production"
      },
      "timeout": 10000
    },
    "remote-api": {
      "type": "remote",
      "url": "https://mcp.yourcompany.com/sse",
      "headers": {
        "Authorization": "Bearer {env:MCP_API_KEY}"
      },
      "timeout": 5000
    }
  }
}

注意这里用 {env:MCP_API_KEY} 引用环境变量——敏感信息别直接写死在配置里。

#配置选项说明

选项说明必填
typelocal（本地 stdio）或 remote（远程 HTTP/SSE）是
command本地服务器启动命令（必须是数组格式）local 必填
url远程服务器 URLremote 必填
environment环境变量（支持 {env:VAR} 语法）否
headersHTTP 请求头（支持 {env:VAR} 语法）否
cwd工作目录否
timeout超时时间（毫秒），默认 5000否
enabled是否启用，默认 true否

#四、Plugins（插件）

#什么是 Plugin？

插件可以扩展 OpenCode 的功能，包括自定义工具、钩子和集成。

如果说自定义工具 / MCP 是给 AI「加外设」，插件则是给 OpenCode 这个「操作系统」本身装软件——它可以挂钩子、扩展工具、接入第三方服务。

#使用 npm 插件

{

  ]

在 .opencode/plugins/ 或 ~/.config/opencode/plugins/ 目录下放置插件文件。

#管理插件

# 安装插件

# 安装到全局配置

#十一、上下文压缩

当对话过长时自动压缩：

{
  "$schema": "https://opencode.ai/config.json",
  "compaction": {
    "auto": true,
    "prune": false,
    "reserved": 10000
  }
}
字段说明
auto上下文满时自动压缩（默认 true）
prune删除旧工具输出以节省 token
reserved压缩时保留的 token 缓冲区
💡 小贴士：可以把压缩想成「收拾行李箱」——对话太长时，AI 自动把前面讨论过的内容打包压缩，腾出空间装新话题；reserved 就是给新内容预留的「空位」。

模板解决「能干活」，技巧解决「干得快」。下面七招，每一招配一个真实案例，学会即用。

#1. 使用 @ 引用文件

@UserService.java 这个类有什么问题？

#2. 分步骤任务

第一步：创建实体类
第二步：创建 Repository
第三步：创建 Service
第四步：创建 Controller
案例： 把「写一个用户模块」拆成四步让 AI 逐步执行——每步都能确认、能纠正，出错时也清楚是哪一步的问题，而不是让 AI 一口气糊一大坨、错了全推倒重来。

#3. 提供上下文

案例： 只说「帮我优化这个查询」，AI 只能靠猜；补上「Spring Boot 3.2 + JPA + MySQL」，AI 直接给出对版本、对框架的方案，少走一轮「不对，我用的是 JPA」的来回。

#OpenCode TUI 内置命令详解

#一、概述

你是否遇到过这样的场景：在输入框里打了个 /，发现里面藏着 OpenCode 的全部"快捷指令"？斜杠命令就是终端里的快捷指令——它把"配置 API 密钥、压缩上下文、分享会话"这类常用操作，全部收进一个以 / 开头的输入框里。跟聊天软件里输入 / 弹出的快捷菜单一个道理：不用记菜单在哪，也不用翻文档，打一个斜杠，所有"按钮"就都浮现出来了。

在 OpenCode TUI（终端界面）中，输入 / 可以查看所有可用命令。本文档详细介绍每个内置命令的含义、作用和使用场景。

快捷键速查请查看 10-快捷键速查.md。

#二、特殊语法

正式介绍命令之前，先认识两种"夹带私货"的写法：@ 和 !。它们不是独立命令，而是在普通消息里就能用的语法，能让每次提问都更省力。

#文件引用 @

@ 的用途是"把文件拉进对话"。就像聊天时 @ 一位好友把他叫进来一样，在消息里 @ 一个文件，OpenCode 会自动模糊搜索项目中的文件，并把文件内容带入对话上下文——不用再手动复制粘贴大段代码。

输入：

@UserService.java 这个类有什么问题？

效果： OpenCode 模糊搜索到 UserService.java，把它的内容加载进上下文后再回答"有什么问题"，而不是凭空猜。

只记得路径的一部分？没问题，直接写完整路径也能精确命中：

帮我分析 @src/main/java/com/example/UserService.java 的性能

还可以引用配置好的 references：

Compare our setup with @docs/README.md

#Shell 命令执行 !

! 的用途是"在终端里跑命令，再把结果喂给 AI"。消息开头写 !，OpenCode 会先执行后面的 shell 命令，并把输出自动添加到对话上下文中。

输入：

!ls -la

效果： 命令先执行，ls -la 的输出进入上下文，AI 基于真实的目录内容继续回答。

输入：

!git status

效果： 工作区状态自动同步给 AI——不用自己粘贴 git status 的输出，它自己就能看到。

💡 小贴士：想搞清楚"现在改到哪一步了"，一句 !git status 加 !git diff --stat，AI 就能在完全知情的情况下干活。

#三、命令详解

#分组速查表

内置命令看着多，其实按用途分四组就很好记：连接（接入模型）、会话（管理对话）、编辑（写消息与反悔）、分享（把对话带出去）。记不住细节没关系，先记住"想干什么，去哪个组找"。

分组命令一句话作用
连接/connect、/models、/init配 API 密钥、选模型、初始化项目
会话/new、/sessions、/compact、/exit开新会话、切换、压缩、退出
编辑/editor、/undo、/redo用外部编辑器写消息、撤销、重做
分享/share、/unshare、/export发分享链接、取消分享、导出对话
显示辅助/details、/help、/themes、/thinking工具详情、帮助、主题、思考过程

下面按分组逐条详解。

#/connect - 连接提供商

添加或配置 LLM 提供商的 API 密钥。

使用场景： 第一次安装 OpenCode、还没配过任何密钥时；或者要接入一个新的模型提供商时。执行 /connect 会弹出提供商列表，选好后输入 API 密钥即可。

/connect

执行后会显示提供商列表，选择后输入 API 密钥。

支持的提供商： Anthropic、OpenAI、DeepSeek、GitHub Copilot、OpenCode Zen 等 75+ 提供商。

#/models - 列出模型

显示所有可用的模型列表——接入了哪些提供商、能用哪些模型，一目了然。

使用场景： 想确认"我到底能用哪些模型"，或者刚接入了新提供商、想看它带来了哪些模型时。

/models

输出格式： provider/model

anthropic/claude-sonnet-4-5
openai/gpt-4o
deepseek/deepseek-v4-pro

#/init - 初始化项目

引导式创建或更新 AGENTS.md 文件。

使用场景： 新 clone 一个项目，让 OpenCode 自动生成一份"项目说明书"（AGENTS.md）。之后每次会话它都先读这份说明书再干活，不用每次重新解释项目背景。

执行过程：

  1. 分析项目结构
  2. 识别技术栈
  3. 生成 AGENTS.md 文件
  4. 建议提交到 Git

#/new - 新建会话

开始一个新的会话，清除当前对话历史。别名： /clear

使用场景： 上一个任务干完了，想开一个干净的新对话；或者当前对话被"聊乱了"、上下文里全是无关内容，直接重启。

/new

注意： 之前的会话仍然可以通过 /sessions 访问。

#/sessions - 列出会话

列出所有会话，支持切换。别名： /resume, /continue

使用场景： 昨天聊到一半的会话，今天想接着聊——/sessions 列出所有历史会话，选中即可继续。

/sessions

会话信息： 会话 ID、创建时间、最后活动时间、消息数量。

#/compact - 压缩会话

压缩当前会话的上下文，减少 token 使用量。别名： /summarize

使用场景： 想象一段对话开了 3 个小时、来回几十轮，AI 的回复越来越慢、上下文塞得越来越满——/compact 就像"把行李箱重新打包一遍"：丢掉重复的细节，保留关键结论，轻装继续。

  • 对话过长，响应变慢
  • 需要释放上下文空间
  • 想要总结之前的讨论
/compact

⚠️ 注意： 压缩后无法恢复原始对话内容。重要对话建议先 /export。

#/editor - 打开外部编辑器

#OpenCode CLI 命令行命令详解

#一、概述

可以这样理解：TUI 是"给人用的界面"，而 CLI 是"给程序用的界面"。OpenCode CLI 允许通过命令行与 OpenCode 交互，支持脚本化和自动化操作——把 OpenCode 塞进 shell 脚本、CI 流水线，或者深夜的定时任务里，它都能一声不吭地干完活。直接运行 opencode 会启动 TUI，也可以使用子命令执行特定操作。

#三、各命令详解

#1. opencode - 启动 TUI

作用： 启动 OpenCode 终端用户界面。

语法：

opencode [project]

示例：

# 启动当前目录
opencode

# 启动指定目录
opencode /path/to/project

# 继续上次会话
opencode --continue

# 继续指定会话
opencode --session abc123

# 使用指定模型
opencode --model anthropic/claude-sonnet-4-5

# 自动批准权限
opencode --auto

参数：

参数缩写说明
--continue-c继续上次会话
--session-s指定会话 ID
--fork-分叉会话（与 --continue 或 --session 配合）
--prompt-直接使用提示词
--model-m指定模型
--agent-指定 Agent
--auto-自动批准权限
--port-监听端口
--hostname-监听主机
--mdns-启用 mDNS
--mdns-domain-自定义 mDNS 域名
--cors-额外 CORS 来源

#2. opencode run - 非交互式运行

作用： 直接执行提示词，不启动 TUI。适合脚本和自动化。

把它当"脚本工具"用： opencode run 就像一台没有屏幕的自动售货机——投一句话进去，它干完活把结果输出到 stdout，然后安静退出，全程不需要人盯着。这正是 CI 想要的场景：每次 PR 合入前，GitHub Actions 里跑一句 opencode run "审查 PR #123 的代码"，让 AI 自动出一份代码审查意见，再结合现有测试把把关。它可以一条命令一问，也可以用 shell 循环把整个目录的文件批量过一遍。

语法：

opencode run [message..]

示例：

# 直接提问
opencode run "解释一下 JavaScript 的闭包"

# 分析代码
opencode run "分析 src/main/java 目录下的代码结构"

# 生成代码
opencode run "创建一个 Spring Boot REST API"

# 使用指定模型
opencode run --model anthropic/claude-sonnet-4-5 "解释这段代码"

# 继续上次会话
opencode run --continue "继续上次的任务"

# 附加文件
opencode run --file UserService.java "审查这个文件"

# JSON 格式输出
opencode run --format json "列出所有 API 端点"

参数：

参数缩写说明
--command-指定要运行的命令
--continue-c继续上次会话
--session-s指定会话 ID
--fork-分叉会话
--share-分享会话
--model-m指定模型
--agent-指定 Agent
--file-f附加文件
--format-输出格式：default 或 json
--title-会话标题
--attach-连接到运行中的服务器
--password-p基本认证密码
--username-u基本认证用户名
--dir-工作目录
--variant-模型变体
--thinking-显示思考过程
--auto-自动批准权限

#3. opencode serve - 启动无头服务器

作用： 启动 HTTP 服务器，提供 API 访问，无 TUI 界面。

典型场景——"一台机器跑服务、多台机器连上去"： 公司里一台配置好的高性能机器执行 opencode serve，把模型、API 密钥、配置都放在这一台；同事们的笔记本只要用 opencode attach 连上去，就能共享同一个后端，不用每个人各自配一遍密钥。

语法：

opencode serve

示例：

# 启动默认服务器
opencode serve

# 指定端口
opencode serve --port 4096

# 监听所有接口
opencode serve --hostname 0.0.0.0

# 启用 mDNS
opencode serve --mdns

# 设置密码保护
OPENCODE_SERVER_PASSWORD=mypassword opencode serve

使用场景：

  • 远程访问 OpenCode
  • 集成到其他工具
  • 多客户端共享同一后端

参数：

参数说明
--port监听端口
--hostname监听主机
--mdns启用 mDNS 发现
--mdns-domain自定义 mDNS 域名
--cors额外 CORS 来源

#5. opencode attach - 连接远程服务器

作用： 连接到已运行的 OpenCode 服务器。

接上一条： serve 负责"跑起来"，attach 负责"连上去"。服务器已经在远端跑着，本地用 opencode attach http://10.20.30.40:4096 接上，TUI 照常用；多个终端还能共享同一个会话——在办公室连上接着聊，回家再连，还是那个上下文。

语法：

opencode attach [url]

示例：

# 连接到本地服务器
opencode attach http://localhost:4096

# 连接到远程服务器
opencode attach http://10.20.30.40:4096

# 带认证连接
opencode attach http://localhost:4096 --username opencode --password mypass

# 继续指定会话
opencode attach http://localhost:4096 --session abc123

使用场景：

  • 远程服务器已启动，本地连接使用 TUI
  • 多个终端共享同一会话

#6. opencode agent - 管理 Agent

作用： 创建和管理自定义 Agent。

  • Agent 名称
  • 描述
  • 模式（primary/subagent）
  • 权限
  • 使用的模型

非交互式创建：

  --path .opencode/agents/java-expert.md \
  --description "Java 开发专家" \
  --mode primary \
  --permissions bash,read,edit \
  --model anthropic/claude-sonnet-4-5

#OpenCode 自定义命令详解

#一、概述

每天是不是都在重复输入类似的提示词？"运行测试并分析失败原因""审查这个文件的代码质量""给这段代码补单元测试"……与其每次都手打一遍，不如把它们做成快捷指令：一条 /命令 就把整套话术、参数、甚至 shell 命令都替你说完。就像手机输入法里的自定义短语——打两个字母，蹦出一整句话。

OpenCode 允许创建自定义命令，将常用操作封装为可复用的命令。支持 JSON 配置和 Markdown 文件两种方式。

创建命令后，在 TUI 中输入 /命令名 即可执行。

#二、创建方式

#方式 1：JSON 配置

在 opencode.json 中使用 command 选项——适合集中管理、配置简短命令：

{
  "$schema": "https://opencode.ai/config.json",
  "command": {
    "test": {
      "template": "运行完整测试套件，生成覆盖率报告，分析失败的测试。",
      "description": "运行测试并生成覆盖率报告",
      "agent": "build",
      "model": "anthropic/claude-haiku-4-5"
    }
  }
}

#方式 2：Markdown 文件

在以下目录创建 .md 文件：

  • 全局： ~/.config/opencode/commands/
  • 项目： .opencode/commands/

文件名即命令名。例如 test.md 创建 /test 命令。

文件格式：

---
description: 命令描述
agent: build
model: anthropic/claude-sonnet-4-5
---

这里是提示词模板内容...

#三、配置选项

选项说明默认值
template / 文件内容发送给 LLM 的提示词（必填）-
description命令描述（显示在 TUI）-
agent执行命令的 Agent当前 Agent
model使用的模型默认模型
subtask是否作为子任务执行false

#四、模板语法

模板是命令的"灵魂"：它不只是固定话术，还能接收参数、执行命令、引用文件。下面逐个语法配"输入 → 替换结果"的对照。

#1. 参数占位符 $ARGUMENTS

$ARGUMENTS 接收所有参数，适合"参数不多、一股脑塞进去"的场景：

---
description: 创建组件
---

创建一个名为 $ARGUMENTS 的 React 组件，包含 TypeScript 支持。

输入： /my-component Button

替换结果： $ARGUMENTS 被替换为 Button，实际发给 LLM 的提示词是：

创建一个名为 Button 的 React 组件，包含 TypeScript 支持。

#2. 位置参数 $1, $2, $3...

$1、$2、$3 按位置接收单独的参数，适合"每个参数各有用处"的场景：

---
description: 创建文件
---

创建文件 $1，放在 $2 目录，内容如下：
$3

输入： /create-file config.json src "{ \"key\": \"value\" }"

替换结果：

  • $1 = config.json
  • $2 = src
  • $3 = { "key": "value" }

实际发给 LLM 的提示词变成：

创建文件 config.json，放在 src 目录，内容如下：
{ "key": "value" }

#3. Shell 命令输出 !command

反引号里写 shell 命令，执行后的输出会被替换进模板——让 AI 基于真实数据干活，而不是凭记忆猜：

---
description: 分析测试覆盖率
---

当前测试结果：
!`npm test`

基于这些结果，建议如何提高覆盖率。

输入： 执行该命令（假设命令名为 /coverage）

替换结果： 模板中的 ` !npm test ` 会被实际执行，测试输出（通过/失败、覆盖率数字等）替换进原位置，AI 直接对着真实测试结果提建议。

再看一个结合 Git 的例子：

---
description: 审查最近变更
---

最近的 Git 提交：
!`git log --oneline -10`

审查这些变更并提供改进建议。

输入： 执行该命令（假设命令名为 /recent-review）

替换结果： git log --oneline -10 的最近 10 条提交记录自动进入上下文，AI 基于它们逐条审查。

#4. 文件引用 @filename

@ 后面跟文件名，文件内容会被读入上下文：

---
description: 审查组件
---

审查 @src/components/Button.tsx 中的组件。
检查性能问题并提供改进建议。

输入： 执行该命令（假设命令名为 /review-component）

替换结果： @src/components/Button.tsx 被替换为该文件的完整内容，AI 直接审查真实代码，不用你复制粘贴。

#五、实战示例

下面 8 个示例可以直接复制到自己的项目里用，每个都标注了"解决什么问题"。

#示例 1：运行测试

解决什么问题： 不用手敲 mvn test 再复制粘贴输出，一条 /test 把"跑测试 → 分析失败 → 给修复建议"全包了。

文件： .opencode/commands/test.md

---
description: 运行测试并分析结果
agent: build
---

运行 Maven 测试套件：
!`mvn test`

分析测试结果：
1. 列出失败的测试
2. 分析失败原因
3. 提供修复建议

使用： /test

#示例 2：代码审查

解决什么问题： 想让 AI 帮你过一遍代码，但每次都要重新讲一遍审查标准？把标准写进命令，/review 文件路径 就按同一套标准审查。

文件： .opencode/commands/review.md

---
description: 审查代码质量
agent: plan
---

请审查以下代码：

@${ARGUMENTS}

审查要点：
1. **安全性** - SQL 注入、XSS、敏感信息泄露
2. **性能** - N+1 查询、不必要的循环
3. **可维护性** - 命名规范、代码重复
4. **异常处理** - 是否完整、是否恰当

输出格式：
### 严重问题

#二、Leader 键机制

默认 Leader 键： ctrl+x

把 Leader 键想成家电的总开关：先按 ctrl+x 把开关打开，再按一个"按钮"（后续键），功能就启动了。比如 ctrl+x + c，就是"开总开关 → 按 c 键"→ 压缩当前会话。功能执行完毕，开关自动归位，下次继续用。

工作方式：

  1. 按下 ctrl+x
  2. 在 2 秒内按下后续键
  3. 执行对应操作
⚠️ 按下 ctrl+x 后要尽快按后续键——超过 2 秒开关就自动关掉了（超时时间就是配置里的 leader_timeout，默认 2000 毫秒）。

自定义 Leader 键：

{
  "$schema": "https://opencode.ai/tui.json",
  "keybinds": {
    "leader": "ctrl+x",
    "leader_timeout": 2000
  }
}

#Agent 与 Subagent 详解

#一、概述

把主 Agent 想成项目经理，子 Agent 想成外包团队。你只需要跟项目经理对话：提需求、看结果。项目经理收到任务后，自己能搞定的就自己干，需要专精技能的部分就派给相应的外包小组——审查派给审查组、测试派给测试组、文档派给文档组。各组把成果交回来，由项目经理整合成一份完整答复递给你。

Agent 是 OpenCode 中专门化的 AI 助手，可以配置不同的模型、提示词和工具权限。理解 Agent 是高效使用 OpenCode 的关键。

OpenCode 有两种类型的 Agent：

  • 主 Agent（Primary）：直接交互的助手，用 Tab 键切换
  • 子 Agent（Subagent）：被主 Agent 调用或用 @ 手动调用的专门助手

#二、内置 Agent

#主 Agent

Agent说明默认权限
build构建代码（默认）全部工具可用
plan制定计划和分析文件修改和 bash 默认需要确认

build 是默认的主 Agent，拥有全部工具权限，适合日常开发工作。

plan 是受限的主 Agent，设计用于分析和规划。它默认拒绝文件修改，bash 命令需要确认。适合：

  • 探索不熟悉的代码库
  • 制定修改方案
  • 代码审查（不实际修改）

#子 Agent

Agent说明特点
general通用子 Agent全部工具权限（除 todowrite），可并行执行多个任务
explore只读探索不能修改文件，快速搜索代码库
scout外部文档研究只读，可克隆依赖仓库到缓存中检查源码
💡 三个内置子 Agent 都像"侦察兵"：explore 在你的代码库里侦察，scout 去外部世界（依赖仓库、文档）侦察，都是只读的，不用担心它们把项目改坏。

#系统内部 Agent

Agent用途
compaction压缩长上下文为摘要（自动运行）
title生成会话标题（自动运行）
summary创建会话摘要（自动运行）

这些是隐藏的系统 Agent，不会出现在 UI 中——它们像幕后的工作人员，默默负责压缩上下文、起标题、做摘要，你几乎感觉不到它们的存在。

#切换主 Agent

一句话记住两者的分工：Build 负责"动手"，Plan 负责"动脑"。想清楚再动手时，先切到 Plan 聊方案。

#permission 细粒度控制

Agent 的权限可以覆盖全局配置，支持对象语法：

{
  "agent": {
    "build": {
      "permission": {
        "bash": {
          "*": "ask",
          "git status*": "allow",
          "git push*": "deny"
        }
      }
    }
  }
}

这段配置的意思是：默认所有 bash 命令都先询问（ask），但 git status 这类只读命令直接放行（allow），git push 这类危险命令直接拒绝（deny）——把"默认谨慎 + 白名单放行 + 黑名单拦截"组合在一起。

Markdown Agent 中：

---
permission:
  edit: deny
  bash:
    "*": ask
    "git diff*": allow
  webfetch: deny
---

#task 权限（控制子 Agent 调用）

{
  "agent": {
    "orchestrator": {
      "permission": {
        "task": {
          "*": "deny",
          "orchestrator-*": "allow",
          "code-reviewer": "ask"
        }
      }
    }
  }
}

task 权限专门管「这个 Agent 能调用哪些子 Agent」，逐条翻译上面的配置：

  • "*": "deny" —— 默认拒绝：除了下面明确放行的，任何子 Agent 都不许调；
  • "orchestrator-*": "allow" —— 通配放行：名字以 orchestrator- 开头的子 Agent 可以直接调（比如 orchestrator-code）；
  • "code-reviewer": "ask" —— 每次询问：调用 code-reviewer 时先征求你的同意再执行。
⚠️ 别把 task 权限和子 Agent 自己的工具权限搞混：task 管的是"能不能请这个人"，子 Agent 的 edit / bash 权限管的是"请来之后能碰什么"——一个是门禁，一个是进门后的规矩。

#子 Agent 嵌套深度

控制子 Agent 可以调用其他子 Agent 的深度：

{
  "$schema": "https://opencode.ai/config.json",
  "subagent_depth": 2
}
  • 0 - 禁止子 Agent：谁都不能调用子 Agent，@ 手动调用也不生效
  • 1 - 允许一级子 Agent（默认）：主 Agent 可以派子 Agent，子 Agent 干完就交差，不能再往下转包
  • 2 - 允许两级嵌套：子 Agent 自己也能调用子 Agent——就像外包团队又把部分活转包给了二级分包商

深度越深，分工越细，但上下文占用和成本也会跟着涨，一般场景用默认的 1 就够了。

#1. 选择合适的 mode

#2. 为不同任务使用不同模型

  • 复杂推理任务 → 使用更强的模型（如 claude-sonnet-4-5）
  • 简单搜索任务 → 使用更快的模型（如 claude-haiku-4-5）

#Skills 技能详解

#一、概述

想象你入职一家新公司，老员工递给你一本《标准作业手册》：泡咖啡有 5 步、写周报有 3 段、走报销有 4 个流程。照着手册做，哪怕没干过也不会跑偏。Skill 就是给 AI 的「SOP 标准作业流程」：把一套多步骤工作流提前写成指令，Agent 遇到匹配的任务就自动"翻开手册"，按标准流程执行。

Skill 是预定义的工作流或指令集，Agent 可以按需加载。当 Agent 识别到任务匹配某个 Skill 时，会自动加载该 Skill 的指令来完成工作。

Skills 让你可以：

  • 将复杂的多步骤流程标准化
  • 在多个项目间复用最佳实践
  • 团队共享工作流规范
  • 让 AI 按照特定的步骤和标准执行任务

#二、文件位置

技能文件放在以下目录的 <名称>/SKILL.md 中：

位置路径说明
项目级.opencode/skills/<名称>/SKILL.md仅当前项目可用
全局级~/.config/opencode/skills/<名称>/SKILL.md所有项目可用
Claude 兼容.claude/skills/<名称>/SKILL.md与 Claude Code 兼容
Agent 兼容.agents/skills/<名称>/SKILL.md与 Agent 平台兼容

每个技能一个目录，目录里必须有 SKILL.md——这个文件就是"手册正文"。

目录结构示例：

.opencode/
├── skills/
│   ├── code-review/
│   │   └── SKILL.md
│   ├── test-generation/
│   │   └── SKILL.md
│   └── documentation/
│       └── SKILL.md

### 建议改进

💡 一个 SKILL.md 分两部分看：开头 --- 之间的 frontmatter 是技能的"身份证"——写清楚名字（name）和用途（description）；下面正文是技能的"操作手册"——写清楚具体怎么做、输出什么格式。Agent 先"刷身份证"判断要不要用，用了再照着"操作手册"执行。

### 第一步：静态分析
检查以下漏洞模式：
- SQL 注入
- XSS
- CSRF
- 路径遍历

### 第二步：依赖检查
运行 `npm audit` 检查已知漏洞。

### 第三步：配置审查
检查环境变量、密钥管理、CORS 配置。

### 第四步：输出报告

## 输出格式

| 1 | 高危 | SQL 注入 | user.ts | 42 |


### 输出
存在 SQL 注入风险，应使用参数化查询：
```typescript
const query = 'SELECT * FROM users WHERE id = ?';
db.query(query, [userId]);
```

#六-B、在 Agent 中加载 Skill

Agent 加载 Skill 有两种方式：原生 skill 工具和 load_skills 参数。

#1. 原生 skill 工具（按需加载）

Agent 在运行时根据任务描述自动发现并加载匹配的 Skill：

# Agent 内部工作流程
1. 启动时扫描所有 Skill 目录
2. 将可用 Skill 列表添加到 skill 工具描述中
3. 根据用户任务判断是否需要加载 Skill
4. 调用 skill({ name: "skill-name" }) 加载完整内容
5. 将 Skill 正文（不含 frontmatter）注入到对话上下文

使用示例：

# 用户消息
使用 code-review 技能审查这个文件

# Agent 内部调用
skill({ name: "code-review" })

#2. load_skills 参数（子 Agent 委托）

在 Oh-My-OpenCode 插件的 task() 工具中，可以指定子 Agent 加载的 Skill：

# 基本用法
task(
    category="writing",
    load_skills=["mintlify", "doc-author"],  # 要加载的 Skill
    description="编写 API 文档",
    prompt="为认证端点编写完整的 API 文档",
    run_in_background=False
)

# 不加载 Skill
task(
    category="quick",
    load_skills=[],
    description="修复拼写错误",
    prompt="修复 README.md 第 45 行的拼写错误",
    run_in_background=False
)

#3. 原生 Skill vs load_skills 对比

方面原生 skill 工具load_skills 参数
触发时机Agent 运行时决定创建任务时指定
加载方式按需、懒加载急切、任务启动时加载
上下文当前 Agent 的上下文委托子 Agent 的上下文
使用场景交互式探索自动化委托
一句话总结： 原生 skill 工具是"现场按需点菜"，load_skills 是"开席前就订好菜"。日常对话用前者，批量编排子 Agent 时用后者。

#4. 权限控制

通过 permission.skill 配置控制 Agent 可以访问哪些 Skill：

{
  "permission": {
    "skill": {
      "*": "allow",
      "internal-*": "deny",
      "experimental-*": "ask"
    }
  }
}

按 Agent 配置：

{
  "agent": {
    "plan": {
      "permission": {
        "skill": {
          "internal-*": "allow"
        }
      }
    }
  }
}

#5. 禁用 Skill

在 Agent 配置中禁用：

{
  "agent": {
    "plan": {
      "tools": {
        "skill": false
      }
    }
  }
}

在 Agent frontmatter 中禁用：

---
tools:
  skill: false
---

#七、与自定义命令配合

Skills 适合定义复杂的工作流，而自定义命令适合快速触发。

推荐搭配：

  • 创建 Skill 定义详细的工作流
  • 创建对应的自定义命令快速触发 Skill
// opencode.json
{
  "command": {
    "review": {
      "template": "使用 code-review 技能审查 @${ARGUMENTS}",
      "description": "代码审查"
    }
  }
}

这个组合就像「自定义命令是快捷按钮，Skill 是按钮背后真正执行的流程」——平时只按按钮，不用记流程。

#八、最佳实践

#1. description 要精确

description 是 Agent 判断是否加载技能的依据。写得越精确，匹配越准确。

好： description: Spring Boot 项目代码审查，关注安全、性能和规范

差： description: 审查代码

为什么差？"审查代码"四个字太宽泛——Agent 既说不清该在什么场景触发它，也分不清它和别的审查类技能有什么区别；而精确的 description 就像包装盒上的产品说明，写清了"对象（Spring Boot 项目）+ 内容（代码审查）+ 关注点（安全、性能、规范）"，Agent 才能在对的场景里一眼选中它。

#2. 指令要具体

不要只说"检查代码质量"，要列出具体检查什么、怎么检查、输出什么格式。

#3. 保持单一职责

一个 Skill 只做一件事。不要把代码审查、测试生成、文档编写塞进同一个 Skill。

#4. 引用项目规范

使用 {file:./path} 引用项目的编码规范、架构文档等，让 AI 了解项目上下文。

#5. 定期更新

随着项目演进，及时更新 Skill 的内容，保持与项目实践一致。

#九、故障排除

#Skill 未被加载

  • 检查 description 是否足够精确
  • 确认 SKILL.md 文件在正确的目录结构中
  • 检查 frontmatter 格式是否正确

#Skill 执行效果差

  • 正文指令是否足够具体
  • 是否包含了输出格式定义
  • 是否有示例供参考

#路径引用失效

  • {file:./path} 的路径相对于 SKILL.md 文件位置
  • 使用 . 表示当前目录，.. 表示上级目录
