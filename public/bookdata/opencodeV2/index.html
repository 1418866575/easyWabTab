#第 1 章 认识 OpenCode 2.0

本章目标：理解 OpenCode 是什么、V2 的客户端/服务端架构、V1 到 V2 的关键变化，并完成安装。

#1.1 OpenCode 是什么

OpenCode 是一个开源的 AI 编程 Agent。它不只是“在终端里聊天”，而是能：

  • 读取、搜索、编辑项目文件；
  • 执行 Shell 命令并读取输出；
  • 调用 MCP 工具、加载 Skills、访问外部文档；
  • 以主 Agent 和子 Agent 协作完成多步骤任务；
  • 通过 TUI、桌面端、Web 端或 HTTP API 使用同一套会话与配置。

它支持多家模型提供商（Anthropic、OpenAI、Google、OpenRouter、本地 Ollama/LM Studio/vLLM 等），也提供 OpenCode 自家的模型目录与 Console 服务。

#1.2 V2 的核心架构

V2 是明确的 客户端 / 服务端 架构：

┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│   TUI 客户端  │   │ Desktop/Web  │   │ 你的脚本/CI   │
└──────┬───────┘   └──────┬───────┘   └──────┬───────┘
       │                  │                  │
       └──────────┬───────┴──────────────────┘
                  ▼
        ┌─────────────────────┐
        │  OpenCode 后台服务    │
        │  会话 / 配置 / 权限   │
        │  插件 / 工具 / 模型   │
        └──────────┬──────────┘
                   ▼
        ┌─────────────────────┐
        │ 模型 Provider / MCP  │
        │ 文件系统 / Shell     │
        └─────────────────────┘

几个直接后果：

  1. 会话属于服务，不属于某个终端窗口。 关掉 TUI 不会丢会话，换客户端还能继续。
  2. 多个客户端共享同一份配置、插件和权限状态。
  3. 默认只有一个后台服务，首次运行会自动发现或启动；也可以用 --standalone 启动私有服务。
  4. 集成应该走 HTTP API，而不是去操作内部文件或数据库。

查看服务状态：

opencode service status
opencode api get /api/info

#1.3 V2 与 V1 的三个破坏性变更

V2 的目标是“大部分 V1 配置继续可用”，但有三处是故意不兼容的：

变更影响你需要做什么
插件 API 重写V1 插件实现无法运行按 V2 插件 API 重写入口、Hook、工具
Server API / 客户端重构调用 V1 API 的集成失效迁移到 @opencode/client 与 V2 API
终端客户端配置改为单个 cli.json不再有分层 tui.json(c)首次启动会自动迁移，项目级客户端配置不再支持

除此之外，V2 还调整了大量配置字段，例如：

  • permission → permissions（有序数组）；
  • agent / mode → agents；
  • mcp 平铺 → mcp.servers；
  • plugin → plugins；
  • command → commands；
  • skills.paths + skills.urls → skills 数组；
  • snapshot → snapshots，attachment → media；
  • 模型引用支持 provider/model#variant。

完整对照见第 20 章。

重要：V1 与 V2 默认不再并存，且共用同一批配置路径。不要用 V1 去读已经改成 V2 原生格式的文件。

#1.4 V2 的几个“默认值变化”

这些变化容易让 V1 用户踩坑：

  • Todos 默认关闭：需要 "experimental": { "todo": true } 才启用待办工具。
  • 外部目录默认允许：V1 会询问项目外路径；V2 默认放行 external_directory。要恢复询问需显式加规则。
  • LSP 不再运行：V2 接受 lsp 配置，但不启动语言服务器、不提供 LSP 诊断。请改用项目的 lint / typecheck / 编译命令。
  • 压缩按 token 保留：不再使用 tail_turns / prune，改用 compaction.keep.tokens。
  • 权限动作重命名：bash → shell，task → subagent，write / patch → edit。

#第 2 章 第一次运行

本章目标：连接模型、发起第一个会话、掌握最基本的上下文引用与撤销，并理解一次请求的生命周期。

#2.1 在项目里启动

cd ~/code/my-project
opencode

也可以直接指定目录：

opencode ~/code/my-project

首次启动会：

  1. 发现或启动后台服务；
  2. 读取全局与项目配置；
  3. 加载 Agent、命令、技能、插件、MCP；
  4. 打开全屏 TUI。

如果当前目录不是 Git 仓库，大部分功能仍可用，但 /undo 无法恢复文件（快照依赖 Git）。

#2.2 连接模型

在 TUI 输入：

/connect

选择提供商，按提示完成 API Key 或 OAuth 登录。常见选择：

  • Anthropic / OpenAI / Google；
  • OpenRouter；
  • OpenCode Go（订阅制）；
  • GitHub Copilot（设备码登录）；
  • 本地 Ollama / LM Studio / vLLM（通常无需登录）。

连接后选择模型：

/models

模型引用格式是：

provider/model
provider/model#variant

例如：

anthropic/claude-sonnet-5-5
openai/gpt-6.1-sol#high
openrouter/anthropic/claude-sonnet-5.5
ollama/gemma3:4b

也可以只对本次运行指定模型：

opencode run --model anthropic/claude-sonnet-5-5 "解释这个仓库的鉴权流程"

#2.3 第一个会话

在输入框里写：

请先阅读 README 和 package.json，告诉我这个项目如何启动、如何测试。
不要修改任何文件。

按 Enter 发送。OpenCode 会：

  1. 组装系统提示、项目指令（AGENTS.md）、技能与工具定义；
  2. 把请求发给模型；
  3. 模型决定调用哪些工具（读文件、搜索、列目录等）；
  4. 工具结果回填给模型；
  5. 重复直到模型给出最终回答。

这就是一个 turn（回合），内部可能包含多个 step（模型步骤）。

#2.4 把文件放进上下文

输入 @ 会打开文件搜索：

解释 @src/auth.ts 的登录流程

可以指定行范围：

解释 @src/auth.ts#20-45

也可以直接粘贴图片、PDF 或文本文件（桌面端/Web 端支持拖拽）。注意：只有支持对应输入类型的模型才能看到图片或 PDF。

#2.5 只读探索：Plan Agent

按 Shift+Tab 切换 Agent，或输入：

/agents

选择 Plan。Plan 适合：

  • 先理解代码再动手；
  • 产出实施计划；
  • 避免误改文件。

Plan 默认拒绝编辑普通项目文件，但仍可执行受权限控制的 Shell 命令。

一个典型流程：

1. 用 Plan 阅读代码，输出方案。
2. 确认方案后切回 Build。
3. 让 Build 按方案实施。
4. 用 /diff 审查改动。
5. 用 /undo 回退不满意的一步。

#2.7 第一次修改代码

切到 Build Agent，输入：

为 src/utils/date.ts 增加一个 formatRelative 函数：
- 支持传入 Date 或时间戳
- 小于 1 分钟显示“刚刚”
- 小于 1 小时显示“x 分钟前”
- 其他情况显示本地日期
同时补充单元测试，并运行测试。

观察几件事：

  • 模型是否会先读现有代码风格；
  • 修改后是否运行了测试；
  • 权限提示出现在哪一步；
  • /diff 中改了哪些文件。

如果结果不满意：

/undo

#2.8 一次请求的生命周期

理解这条链路，后续排错会容易很多：

用户输入
  → 客户端做附件/技能/命令解析
  → 服务端准入（prompt hook）
  → 组装上下文（系统提示 + AGENTS.md + 技能 + MCP 指令 + 历史）
  → 选择模型/变体
  → 模型返回工具调用或文本
  → 权限检查（permissions → 已保存审批 → policies）
  → 执行工具（文件 / Shell / MCP / Web）
  → 结果回填，进入下一步
  → 最终文本 + 快照 + 会话记录

任何一环出问题，都可能表现为“模型没反应”“工具被拒绝”“上下文太长”。第 17 章会按这条链路排查。

#2.11 小结

  • 先 /connect，再 /models，模型引用是 provider/model#variant。
  • @ 引用文件，! 进入 Shell 模式，/ 打开命令。
  • Plan 负责只读探索，Build 负责实施。

#3.1 界面构成

启动 opencode 后，典型界面包含：

  • 会话区：消息、工具调用、思考块、子 Agent 状态。

#3.5 上下文与旁支问题

#/btw

/btw 第 2 步的测试为什么失败？

  • 快速确认一个细节；

#3.7 撤销与重做

操作快捷键命令

/undo 的行为：

  1. 暂存回滚；
  2. 恢复受影响文件；
  3. 把被撤销的提示放回输入框；
  4. 你编辑后重新发送，即确认回滚；
  5. 发送前 /redo 可取消。

注意：

  • 需要 Git 仓库才能恢复文件；
  • 只恢复当前会话目录内、被助手步骤改过的路径；
  • Shell 造成的数据库、服务、Git 提交等副作用不会回滚；
  • 重要工作仍应提交或备份。

#第 4 章 CLI 与自动化

本章目标：掌握 opencode 命令族，把 OpenCode 用于脚本、CI、远程客户端和日常运维。

#4.1 命令总览

opencode [directory]          # 打开 TUI
opencode run "prompt"         # 非交互执行
opencode mini                 # 极简交互界面
opencode pair                 # 打开 Web 连接
opencode serve                # 启动 HTTP 服务
opencode service <cmd>        # 管理后台服务
opencode api <method> <path>  # 调用本地 API
opencode mcp <cmd>            # 管理 MCP
opencode plugin <cmd>         # 管理插件
opencode debug <cmd>          # 诊断
opencode uninstall            # 卸载

所有命令都遵循同一套服务发现与认证流程。多数命令会自动连接共享后台服务，必要时启动它。

#4.2 opencode run：非交互执行

opencode run "解释这个仓库的目录结构"

指定模型：

opencode run --model anthropic/claude-sonnet-5-5 "重构 parseToken"

在目标目录执行：

cd ~/code/api
opencode run "找出所有未处理的 Promise rejection"

常用参数：

opencode run --continue "继续刚才的任务"          # 继续上一个会话
opencode run --session ses_xxx "继续这个会话"     # 指定会话
opencode run --agent reviewer "审查当前改动"      # 指定 Agent
opencode run --format json "输出结构化结果"        # JSON 输出
opencode run --file src/api.ts "解释这个文件"      # 附带文件

--auto 会自动批准未被显式拒绝的权限请求，只建议在隔离、可信的 CI 环境使用。

适合：

  • CI 中的代码审查、变更摘要、文档生成；
  • 一次性问答；
  • 脚本里需要模型输出到 stdout。

注意：run 仍是 Agent，可能调用工具、修改文件、请求权限。非交互环境要提前配置权限，避免卡在审批上。

#CI 示例（只读审查）

opencode run \
  --model anthropic/claude-sonnet-5-5 \
  "审查当前分支相对 main 的改动，只输出问题列表，不要修改文件"

配合只读 Agent 更稳：

{
  "agents": {
    "ci-review": {
      "mode": "primary",
      "model": "anthropic/claude-sonnet-5-5",
      "system": "只做代码审查，不修改文件。输出按严重程度排序的问题。",
      "permissions": [
        { "action": "edit", "resource": "*", "effect": "deny" },
        { "action": "shell", "resource": "*", "effect": "deny" }
      ]
    }
  }
}
opencode run --agent ci-review "审查当前改动"

#4.3 opencode mini：极简界面

opencode mini

适合低带宽、远程终端、嵌入其他工具，或只想要“对话流”而不想全屏 TUI 的场景。

opencode mini --help

可查看会话、模型、Agent、提示、回放等参数。界面行为可在 cli.json 的 mini 组里配置，例如：

{
  "mini": {
    "thinking": "hide",
    "tools": "hide",
    "shell_output": "hide",
    "turn_summary": "show",
    "mono": false
  }
}

#4.4 opencode pair：Web 客户端

opencode pair

输出一次性连接链接，默认 5 分钟内有效。浏览器打开后即可使用 Web 界面。

前提：

  • 共享后台服务可用；
  • 如果禁用了共享服务，pair 不可用。

#4.5 后台服务

默认模式：

opencode                  # 自动发现/启动共享服务
opencode --standalone     # 私有服务，仅本进程使用
opencode --server http://localhost:4096   # 连接指定服务

服务管理：

opencode service status
opencode service start
opencode service stop
opencode service restart

服务配置：

opencode service set env HTTP_PROXY http://proxy.example.com:8080
opencode service get env
opencode service unset env HTTP_PROXY

禁用共享服务（改为每次私有服务）：

opencode service set disabled true
opencode service unset disabled
服务命令用于诊断和运维，不是“改完配置就要重启”。配置会自动重载。

#4.6 opencode serve

显式启动一个 HTTP 服务：

opencode serve
opencode serve --cors http://192.168.1.10:3001

认证：

OPENCODE_PASSWORD=secret opencode serve

V2 中：

  • 用户名固定为 opencode；
  • OPENCODE_PASSWORD 设置密码；
  • OPENCODE_SERVER_PASSWORD 仍兼容；
  • OPENCODE_SERVER_USERNAME 不再支持。

浏览器跨域需要把来源加入 CORS：

opencode service set cors "http://192.168.1.10:3001, https://app.example.com"

#4.7 opencode api：命令行调 API

opencode api get /api/info
opencode api get /api/agent
opencode api get /api/session

带请求体：

opencode api post /api/session/ses_xxx/compact --data '{}'

带请求头：

opencode api get /api/session --header 'X-Example:value'

也可以用 OpenAPI operation ID 调用。完整端点见 https://opencode.ai/v2/docs/api。

opencode api 在找不到健康服务时可能自动启动后台服务。

#创建会话并提问

# 1. 创建会话
opencode api post /api/session --data '{"location":{"directory":"/workspace"}}'

# 2. 发送提示（把返回的 session id 填进去）
opencode api post /api/session/ses_xxx/prompt --data '{"text":"解释这个项目"}'

具体字段以运行中服务的 /openapi.json 为准：

curl http://localhost:4096/openapi.json

# MCP
opencode mcp add context7 --url https://mcp.context7.com/mcp
opencode mcp add context7 --global --url https://mcp.context7.com/mcp
opencode mcp add everything -- npx -y @modelcontextprotocol/server-everything

# 插件

opencode plugin remove opencode-acme-plugin@1.2.0

mcp add 默认写入当前项目配置；加 --global 写入全局配置。

#4.9 opencode debug

opencode debug paths          # 所有路径
opencode debug paths db       # 只打印数据库路径
opencode debug heap-dump      # 运行中服务的内存快照

debug paths 可选：db、home、data、config、cache、state、tmp、bin、log、repos。

heap-dump 只使用已运行的服务，不会启动新服务；写入时服务会短暂暂停。快照可能包含提示、文件内容和凭据，不要公开分享。

#4.10 卸载

opencode uninstall --dry-run
opencode uninstall
opencode uninstall --force

卸载会停止后台服务和持久终端，删除全局缓存目录，但 不会删除 会话数据、配置和状态。

包管理器安装的版本会调用对应包管理器；curl 安装会提示手动删除可执行文件。

#4.11 脚本化实践

#PowerShell：批量生成变更摘要

$branch = git rev-parse --abbrev-ref HEAD
opencode run --model anthropic/claude-sonnet-5-5 `
  "总结分支 $branch 相对 main 的改动，输出 Markdown 列表，不要修改文件"

#Bash：把结果写入文件

opencode run "为 src/ 生成模块级文档，只输出 Markdown" > docs/modules.md

#CI：失败即阻断（示例思路）

set -euo pipefail
opencode run --agent ci-review "审查当前改动，发现严重问题就以 FAIL 开头" | tee review.txt
grep -q '^FAIL' review.txt && exit 1

实际使用时建议：

  • 固定模型和 Agent，避免结果漂移；
  • 关闭自动更新（update: "disable"）；
  • 用只读权限运行审查；
  • 把网络与密钥通过环境变量注入，不写进仓库。

#4.12 退出码与输出

run 主要用于把模型输出写到 stdout，便于管道处理。业务判断不要依赖“模型是否成功”，而应：

  1. 让模型输出结构化标记（如 FAIL / PASS）；
  2. 在脚本里显式检查；
  3. 对关键步骤加自己的测试或 lint。

#4.13 本章练习

  1. 用 opencode run 生成当前仓库的 README 摘要。
  2. 用 --model 指定另一个模型，比较输出。
  3. 启动 opencode serve，用 opencode api get /api/info 验证。
  4. 用 opencode mcp add 添加一个远程 MCP，再 mcp list 查看状态。
  5. 写一个 PowerShell 或 Bash 脚本，把审查结果保存到文件并根据关键字退出非零。

#4.14 小结

  • run 负责非交互，mini 负责轻量交互，TUI 负责完整交互。
  • 共享服务是默认架构，--standalone 和 --server 用于隔离或远程。
  • opencode api 是最方便的本地 API 调试入口。
  • 自动化要固定模型/Agent、收紧权限、显式判断结果。

#第 5 章 配置系统

本章目标：搞清楚 OpenCode 到底读哪些文件、谁覆盖谁、哪些配置属于服务端、哪些属于终端客户端。

#5.1 两类配置，不要混

类型文件作用
服务端 / 项目配置opencode.json 或 opencode.jsonc模型、Agent、权限、MCP、插件、命令、技能等
终端客户端配置~/.config/opencode/cli.json主题、快捷键、Tabs、Diff 外观、通知、Mini 等

关键区别：

  • opencode.json 由后台服务加载，项目级配置生效。
  • cli.json 只属于终端客户端，没有项目级文件，全局唯一。
  • 不要把主题、快捷键写进 opencode.json；也不要指望 cli.json 改变模型或权限。

#5.2 服务端配置的位置

从低到高：

~/.config/opencode/opencode.json(c)           # 全局
<项目>/opencode.json(c)                        # 项目
<项目>/.opencode/opencode.json(c)              # 项目（更高）
/etc/opencode/opencode.json(c)                 # 系统（最高）

Windows 的系统目录是：

%ProgramData%\opencode\opencode.json(c)

macOS 还可读取 MDM 管理的 plist：

/Library/Managed Preferences/<user>/ai.opencode.managed.plist
/Library/Managed Preferences/ai.opencode.managed.plist

系统配置和托管首选项优先级最高；它们还提供 policies，用于强制组织策略。

#5.3 项目配置的发现与合并

OpenCode 从当前目录向上搜索到文件系统根，先合并直接的 opencode.json(c)，再合并 .opencode/opencode.json(c)。

/home/user/projects/acme/
├── opencode.json
└── packages/web/
    ├── opencode.json
    └── src/                ← 在这里启动

按优先级从低到高：

1. ~/.config/opencode/opencode.json
2. /home/user/projects/acme/opencode.json
3. /home/user/projects/acme/packages/web/opencode.json
4. /etc/opencode/opencode.json

含义：

  • 越靠近当前目录的项目配置，覆盖越外层。
  • 所有 .opencode/opencode.json(c) 都覆盖所有直接 opencode.json(c)，即使直接文件更靠近当前目录。
  • 不冲突的字段会保留并合并。
  • 尽量在整棵树里只用一种形式，避免意外覆盖。

#5.4 policies 的优先级是反的

普通设置是“越近越优先”；policies 是“越宽越优先”：

最高：macOS 托管首选项
     系统配置
     Console 工作区
     全局配置
     直接项目配置（外层 > 内层）
最低：.opencode 项目配置（外层 > 内层）

也就是说，全局 deny 一个 Provider，项目里写 allow 也解不开。这是组织治理的基础。

#5.5 JSON 还是 JSONC

两者都支持。JSONC 允许注释和尾逗号：

{
  "$schema": "https://opencode.ai/config.json",
  // 默认模型
  "model": "anthropic/claude-sonnet-5-5",
}

始终保留 $schema，编辑器才能校验字段和自动补全。

#5.6 变量替换

#环境变量

{
  "model": "{env:OPENCODE_MODEL}",
  "providers": {
    "anthropic": {
      "settings": {
        "apiKey": "{env:ANTHROPIC_API_KEY}"
      }
    }
  }
}

变量不存在时替换为空字符串。

#文件内容

{
  "providers": {
    "openai": {
      "settings": {
        "apiKey": "{file:~/.secrets/openai-key}"
      }
    }
  }
}

路径可以相对于配置文件、绝对路径，或以 ~/ 开头。文件不存在时替换为空字符串。

用途：

  • 密钥不落仓库；
  • 多份配置共享片段；
  • CI 注入不同环境的值。

  3. 在项目里创建 .opencode/opencode.json，观察它与根目录 opencode.json 的覆盖关系。
  4. 把主题改到 cli.json，确认它不影响 opencode.json。
  5. 故意写一个错误字段，看编辑器和服务端分别如何提示。

  • 配置自动重载；/reload 可强制刷新。

#第 6 章 模型与 Provider

本章目标：理解模型引用、变体、能力与成本，能连接云提供商、本地模型和自定义 OpenAI 兼容端点。

#6.1 三层概念

Provider（提供商） → Model（模型） → Variant（变体）
  • Provider：Anthropic、OpenAI、OpenRouter、Ollama、你自建的网关。
  • Model：某个具体模型，如 claude-sonnet-5-5、gpt-6.1-sol。
  • Variant：同一模型的命名配置，如低/高推理强度、不同 temperature。

选择时写成：

provider/model#variant

示例：

anthropic/claude-sonnet-5-5
openai/gpt-6.1-sol#high
openrouter/anthropic/claude-sonnet-5.5
ollama/gemma3:4b

规则：

  • Provider ID 到第一个 / 结束，不能包含 / 或 #。
  • Model 可以再包含 /，但不能包含 #。
  • Variant 在 # 之后。
  • Provider 和 Model ID 大小写敏感。

#6.2 连接与选择

TUI：

/connect
/models

/connect 支持：

  • API Key；
  • OAuth（如 GitHub Copilot 设备码）；
  • ChatGPT Plus/Pro 账号；
  • OpenCode Go；
  • 本地服务（通常自动发现）。

/models 只显示：

  • 已启用的模型；
  • 其 Provider 在当前项目中可用；
  • 凭据与配置对当前项目生效。

模型可用性是 项目级 的。A 项目连的账号和配置，不会自动带到 B 项目。

#6.3 默认模型

{
  "$schema": "https://opencode.ai/config.json",
  "model": "anthropic/claude-sonnet-5-5"
}

规则：

  • 已选会话的模型优先于配置默认值。
  • 切换会话模型不会改写配置文件。
  • 根 model 目前不保留 #variant；需要变体时在 Agent、命令或会话中选择。
  • 配置的模型不可用时，回退到最新的可用模型。

#6.4 变体（Variant）

选择变体：

opencode run --model openai/gpt-6.1-sol#high "评审这个迁移方案"

在 Agent / 命令里：

model: anthropic/claude-sonnet-5-5#high

自定义变体：

{
  "providers": {
    "openai": {
      "models": {
        "gpt-6.1-sol": {
          "settings": { "reasoningEffort": "medium" },
          "variants": [
            {
              "id": "fast",
              "settings": { "reasoningEffort": "low" }
            },
            {
              "id": "deep",
              "settings": {
                "reasoningEffort": "high",
                "reasoningSummary": "auto"
              }
            }
          ]
        }
      }
    }
  }
}

每个变体可包含：

  • settings：Provider 包选项；
  • headers：额外请求头；
  • body：请求体字段。

应用顺序：Provider → Model → Variant。嵌套对象合并，数组和标量后者覆盖前者。

#6.5 模型能力与限制

自定义模型时，尽量写准：

{
  "providers": {
    "local": {
      "models": {
        "coder": {
          "modelID": "model-name-on-server",
          "name": "Local Coder",
          "capabilities": {
            "tools": true,
            "input": ["text"],
            "output": ["text"]
          },
          "limit": {
            "context": 32768,
            "output": 8192
          },
          "cost": {
            "input": 0,
            "output": 0
          }
        }
      }
    }
  }
}
  • capabilities.tools：是否支持工具调用。
  • capabilities.input / output：文本、图片等。
  • limit.context / output：上下文与输出上限。
  • cost：每百万 token 的价格，用于显示与预算判断。
  • 未在目录中的模型，OpenCode 会假设支持工具、文本+图片输入、200k 上下文、32k 输出。这些只是回退假设，不是检测结果。

#第 7 章 Agent 系统

本章目标：理解主 Agent、子 Agent、内置 Agent 的行为，能设计可复用的角色与编排流程。

#7.1 Agent 是什么

一个 Agent 由这些部分组成：

  • 系统提示（system）；
  • 模型与变体；
  • 权限规则；
  • 运行模式（primary / subagent / all）；
  • 步数上限、可见性、颜色等展示属性。

Agent 决定“谁来做、能做什么、用什么模型做”。

#7.2 内置 Agent

Agent模式用途
Build（build）primary默认编码 Agent，可改文件、跑命令；读敏感 .env 会询问
Plan（plan）primary只探索和规划，不改普通项目文件；可写 OpenCode 计划文件
General（general）subagent研究、多步骤任务，工具广，但不能继续派子 Agent
Explore（explore）subagent搜索和阅读代码/网页，不编辑

隐藏的维护 Agent：

  • compaction：压缩摘要；
  • title：会话标题；
  • summary：摘要。

它们不能被直接选择。

V2 没有内置 scout Agent。

#7.3 创建自定义 Agent

#Markdown 文件（推荐）

---
description: 审查改动，按严重程度报告问题
mode: subagent
model: anthropic/claude-sonnet-5-5#high
permissions:
  - action: edit
    resource: "*"
    effect: deny
  - action: shell
    resource: "*"
    effect: deny
---

审查当前改动。按严重程度排序，给出文件与行号。
不要修改文件。

保存到：

.opencode/agents/reviewer.md      # 项目
~/.config/opencode/agents/reviewer.md  # 全局

嵌套路径会成为 ID 的一部分：

.opencode/agents/team/reviewer.md → team/reviewer

#JSONC

{
  "$schema": "https://opencode.ai/config.json",
  "agents": {
    "reviewer": {
      "description": "审查改动",
      "mode": "subagent",
      "system": "按严重程度报告问题，不修改文件。",
      "permissions": [
        { "action": "edit", "resource": "*", "effect": "deny" }
      ]
    }
  }
}

#7.4 模式

模式行为
primary作为会话主 Agent，可直接选中
subagent只能通过 subagent 工具在子会话中运行
all两种都可以

新自定义 Agent 省略 mode 时默认 primary。

子 Agent：

  • 使用全新上下文；
  • 可前台或后台运行；
  • 子 Agent 使用自己的权限，不是父 Agent 权限的子集；
  • 父 Agent 的 subagent 权限决定它能启动哪些子 Agent。

示例：只允许编排者启动 reviewer：

{
  "agents": {
    "orchestrator": {
      "permissions": [
        { "action": "subagent", "resource": "*", "effect": "deny" },
        { "action": "subagent", "resource": "reviewer", "effect": "allow" }
      ]
    }
  }
}

#7.5 关键字段

#description

子 Agent 必写。父 Agent 靠它判断何时调用。

description: 审查数据库迁移的安全性

#model

model: anthropic/claude-sonnet-5-5#high

子 Agent 未配置模型时继承父会话模型。

#system

非空值会 替换 该 Agent 的 Provider 基础系统提示，但项目指令、技能、References 仍会追加。

Markdown Agent 的正文就是 system，不要在 frontmatter 再写。

#permissions

{
  "permissions": [
    { "action": "*", "resource": "*", "effect": "deny" },
    { "action": "read", "resource": "src/**", "effect": "allow" }
  ]
}

最后匹配的规则生效，宽规则在前，例外在后。

#steps

steps: 8

限制最大模型步数。到最后一步时，OpenCode 会移除工具并要求模型用文本总结。新的用户输入会重置额度。

#hidden

hidden: true

从列表、交互发现和子 Agent 目录中隐藏。这是可见性，不是安全边界；安全用权限。

#color

color: "#ff6b6b"

六位十六进制。

#disabled

{
  "agents": {
    "plan": { "disabled": true }
  }
}

禁用内置或自定义 Agent。

#request

{
  "agents": {
    "reviewer": {
      "request": {
        "headers": { "x-agent": "reviewer" },
        "body": { "temperature": 0.1 }
      }
    }
  }
}

V2 会保留但 不会发送 给模型。需要采样参数时，配到 Provider、Model 或 Variant 上。

#7.6 合并规则

  • 后加载的标量覆盖先加载的；
  • 请求映射按 key 合并；
  • 权限规则 追加，不是替换；
  • 全局 permissions 先应用，Agent 规则后应用，因此 Agent 可以细化全局规则。

覆盖内置 Agent：

{
  "agents": {
    "build": {
      "permissions": [
        { "action": "shell", "resource": "git push *", "effect": "ask" }
      ]
    }
  }
}

#7.7 默认 Agent

{
  "default_agent": "writer",
  "agents": {
    "writer": { "mode": "primary" }
  }
}

要求：

  • 必须存在；
  • 必须可见；
  • 必须支持 primary。

否则回退到 build，再回退到第一个可用的主 Agent。修改默认值不会改变已有会话已选的 Agent。

#7.8 编排模式

#模式一：主 Agent + 只读评审

Build 实现 → reviewer 子 Agent 评审 → Build 修复

reviewer：

---
description: 只读评审
mode: subagent
permissions:
  - action: edit
    resource: "*"
    effect: deny
---
按严重程度列出问题，附文件与行号。

#模式二：探索者 + 实现者

explore 定位代码 → build 修改 → tester 运行测试

#模式三：编排者

---
description: 拆解任务并分派
mode: primary
permissions:
  - action: subagent
    resource: "*"
    effect: allow
---
先拆解任务，再按需启动 reviewer / tester。
不要自己修改文件。

#模式四：领域专家

  • db-migration：只允许读 schema 和迁移文件；
  • security：只读 + Web 搜索；
  • docs：只改 docs/**。

#7.9 子 Agent 的成本与风险

  • 子 Agent 有独立上下文，会额外消耗 token；
  • 后台子 Agent 的结果会回传父会话；
  • 子 Agent 不会自动继承父权限，必须单独设计；
  • 子 Agent 可能并行读写同一文件，注意冲突；
  • 不要让子 Agent 无限递归：experimental.subagent_depth 默认 1。

#7.10 调试 Agent

  1. /agents 确认 Agent 是否被发现、模式是否正确。
  2. 看系统提示是否被覆盖（Markdown 正文是否为空）。
  3. 看权限规则顺序（最后匹配）。
  4. 用 steps: 3 限制步数，观察它是否按预期收敛。
  5. 用 hidden: true 排除干扰前，先确认不是路径/ID 问题。

#7.11 本章练习

  1. 创建一个只读 reviewer 子 Agent，并让 Build 调用它。
  2. 创建一个 docs Agent，只允许编辑 docs/**。
  3. 给 Agent 配 steps: 5，观察达到上限时的行为。
  4. 用 default_agent 切换默认主 Agent。
  5. 设计一个编排者，只允许启动 reviewer 和 tester。

#7.12 小结

  • Agent = 提示 + 模型 + 权限 + 模式。
  • primary 直接使用，subagent 由父 Agent 调用，all 两者皆可。
  • 子 Agent 独立上下文、独立权限。
  • 权限规则追加，最后匹配生效。
  • 好的 Agent 设计是“窄职责 + 明确权限 + 清晰描述”。

#第 8 章 权限与安全

本章目标：理解 V2 权限模型，写出既安全又不碍事的规则，并用 Policies 做组织级硬约束。

#8.1 权限解决什么问题

权限控制“某个 Agent 能否对某个资源执行某个动作”。三个要素：

{ "action": "shell", "resource": "git push *", "effect": "deny" }
字段含义
action工具或权限动作，如 shell、edit、read
resource路径、命令、URL、查询、技能 ID、Agent ID 等
effectallow、deny、ask

没有规则匹配时，默认是 ask。

#8.2 基本规则

{
  "$schema": "https://opencode.ai/config.json",
  "permissions": [
    { "action": "shell", "resource": "*", "effect": "ask" },
    { "action": "shell", "resource": "git status *", "effect": "allow" },
    { "action": "shell", "resource": "git diff *", "effect": "allow" },
    { "action": "shell", "resource": "git push *", "effect": "deny" }
  ]
}

最后匹配的规则生效。所以：

  1. 宽规则放前面；
  2. 例外放后面；
  3. 不要把 deny 放在会被后面 allow 覆盖的位置。

#8.3 通配符

模式匹配
*零个或多个字符，包括 /
?恰好一个字符
其他字面字符
{
  "permissions": [
    { "action": "edit", "resource": "packages/docs/*.mdx", "effect": "allow" }
  ]
}

路径规则匹配整个规范化路径：

  • 反斜杠转 /；
  • Windows 上大小写不敏感；
  • ~、$HOME 在 read、edit、external_directory 中会展开；
  • Shell 资源是原始命令文本，不展开 ~。

Shell 规则以 * 结尾时，也匹配无参数命令：

{ "action": "shell", "resource": "git status *", "effect": "allow" }

同时匹配 git status 与 git status --short。

#8.4 动作与资源

ActionResource
read项目相对路径或外部绝对路径
editedit/write/patch 的目标路径
glob请求的 glob
grep请求的正则（不是搜索路径）
shell扫描器产生的命令字符串
subagent目标 Agent ID
skill技能 ID
question*
webfetch请求的 URL
websearch搜索查询
external_directory外部目录边界，通常以 /* 结尾
&lt;server&gt;_&lt;tool&gt;MCP 工具
opencode_list_mcp_resourcesMCP 服务名
opencode_read_mcp_resource&lt;server&gt;:&lt;uri&gt;
executeCode Mode 入口

一次操作可能检查多个资源（例如补丁涉及多个文件）：

  • 任一 deny → 拒绝；
  • 否则任一 ask → 询问；
  • 否则允许。

#8.5 默认策略

每个 Agent（包括自定义）都以这组规则开始：

[
  { "action": "*", "resource": "*", "effect": "allow" },
  { "action": "read", "resource": "*.env", "effect": "ask" },
  { "action": "read", "resource": "*.env.*", "effect": "ask" },
  { "action": "read", "resource": "*.env.example", "effect": "allow" }
]

内置 Agent 追加：

Agent追加策略
build允许提问
plan允许提问；拒绝编辑，除非 ~/.opencode/plan 下
general拒绝提问、拒绝启动子 Agent
explore除 Shell、读、glob、grep、Web、外部目录外全部拒绝；.env 读取询问
title / summary拒绝一切
compaction保持基础策略

#8.6 外部目录：V2 的重要变化

V2 默认允许 external_directory，不询问。要恢复 V1 行为：

{
  "permissions": [
    { "action": "external_directory", "resource": "*", "effect": "ask" }
  ]
}

再对特定目录放行或拒绝：

{
  "permissions": [
    { "action": "external_directory", "resource": "*", "effect": "ask" },
    { "action": "external_directory", "resource": "~/projects/reference/*", "effect": "allow" },
    { "action": "read", "resource": "~/projects/reference/*", "effect": "allow" },
    { "action": "edit", "resource": "~/projects/reference/*", "effect": "deny" }
  ]
}

这适用于 read、edit、write、patch。Shell 会先检查外部工作目录和扫描器推断的目录，再检查 shell 资源。

#8.7 Agent 级权限

顶层规则共享，Agent 规则追加：

{
  "permissions": [
    { "action": "shell", "resource": "*", "effect": "ask" },
    { "action": "shell", "resource": "git status *", "effect": "allow" }
  ],
  "agents": {
    "reviewer": {
      "mode": "subagent",
      "permissions": [
        { "action": "edit", "resource": "*", "effect": "deny" }
      ]
    }
  }
}

Agent 规则 不会替换 全局数组，而是接在后面。因此可以细化，但不能凭空放宽被全局 deny 的部分（政策还会再压一层）。

#8.8 审批

当规则解析为 ask，客户端可回复：

选择回复结果
只允许一次once仅本次
总是允许always保存工具建议的模式为项目级 allow
拒绝reject拒绝，并拒绝该会话其他待处理请求

“总是允许”保存的是 项目级持久规则。例如：

shell: git status * → allow

保存的允许规则：

  • 不能覆盖显式 deny；
  • 不同工具建议的模式不同：有的建议 *，Shell 建议命令前缀，技能/子 Agent 建议 ID；
  • 应定期审查，删除过宽的规则。

#8.9 Policies：硬约束

Policies 与权限不同：

  • 只有 allow / deny，不会询问；
  • 只能收紧，不能授权；
  • 在权限规则和已保存审批之后执行；
  • 跨配置文件的优先级是“越宽越高”。

#禁止 Provider

{
  "policies": [
    { "action": "provider.use", "resource": "openai", "effect": "deny" }
  ]
}

被禁的 Provider 会从目录和模型选择中消失。

#硬禁命令

{
  "policies": [

#8.11 Shell 的真实风险

shell 以宿主用户的文件系统、进程和网络权限运行。

这意味着：

  • 命令可以访问项目外文件；
  • 可以启动服务、改数据库、推 Git、发网络请求；
  • 目录推断是“尽力而为”，不要指望模式能识别所有危险命令。

建议：

  1. 默认 ask；
  2. 只对明确的只读命令放行；
  3. 对 git push、rm、curl | sh、sudo 等硬禁；
  4. 高敏感环境使用容器/虚拟机隔离；
  5. 不要把“允许所有 Shell”当成方便。

#8.13 常见误区

误区事实
“hidden 能防止调用”只影响可见性，安全靠权限
“Agent 权限是父权限子集”子 Agent 用自己的权限
“保存的 allow 能覆盖 deny”不能，deny 始终优先
“项目里 allow 能解全局 deny”Policies 优先级相反，不能
“V2 还会询问外部目录”默认允许，需显式加 ask
“权限能沙箱插件”不能，插件代码仍在服务进程内

#8.14 本章练习

  1. 写一组规则：默认询问 Shell，放行 git status/diff/log，禁止 push。
  2. 让 reviewer 只能读、搜索，不能编辑或执行 Shell。
  3. 添加 external_directory 询问规则，验证项目外读取会弹窗。
  4. 用 Policies 全局禁止一个 Provider，确认项目配置无法解开。
  5. 查看已保存审批，删除一条过宽规则。

#8.15 小结

  • 权限是有序规则，最后匹配生效。
  • V2 默认允许外部目录，要主动收紧。
  • ask 支持一次/总是/拒绝；保存的规则是项目级。
  • Policies 是硬约束，只能收紧，组织策略优先。
  • Shell 权限等于宿主用户权限，必须谨慎。

#第 9 章 上下文工程

本章目标：理解模型每一轮到底看到了什么，并用 AGENTS.md、instructions、references、compaction 把上下文管好。

#9.1 上下文不是“越多越好”

一次模型请求大致由这些部分组成：

1. Agent / Provider 系统提示
2. Code Mode 工具指南（启用时）
3. MCP 服务、Reference、Skill 指引
4. 全局与项目 AGENTS.md、配置的 instructions
5. 内置日期与环境信息
6. 会话历史、工具结果、附件
7. 当前用户输入

上下文越长：

  • 成本越高；
  • 延迟越大；
  • 关键信息越容易被淹没；
  • 越容易触发压缩，甚至丢失细节。

上下文工程的目标是：在正确的时机，给模型正确的最小信息。

#9.2 AGENTS.md：项目常驻指令

在项目根目录创建：

# Project instructions

- 修改 TypeScript 后运行 `bun typecheck`。
- 数据库查询统一放在 `src/database`。
- 不要直接编辑生成文件。
- 提交前运行 `bun test`。

提交到仓库，团队成员共享。

#作用范围

OpenCode 加载：

~/.config/opencode/AGENTS.md
<workspace 向上直到 home 的每一层 AGENTS.md>

例如：

~/.config/opencode/AGENTS.md
~/code/my-project/AGENTS.md
~/code/my-project/packages/AGENTS.md
~/code/my-project/packages/web/AGENTS.md  ← 当前工作目录

全部加载，顺序为：

全局
packages/web/AGENTS.md
packages/AGENTS.md
项目根 AGENTS.md

全局文件最先加载，然后从当前工作目录向项目根（或 home）方向逐层加入。它们 合并，不解决冲突。

如果工作目录在项目根之外，只加载全局文件。设置：

OPENCODE_DISABLE_PROJECT_CONFIG=1

可跳过项目 AGENTS.md，但保留全局文件。

V2 只识别 AGENTS.md，不再回退到 CLAUDE.md。

#按需发现

工作目录以下的 AGENTS.md 会在 Agent 探索到该区域时加载：

my-project/
├── AGENTS.md                    ← 初始加载
└── packages/web/
    ├── AGENTS.md                ← 读到该区域时加载
    └── src/app.ts

规则：

  • 越近的越先加载；
  • 同一条指令条目在历史中只保留一次；
  • 如果压缩或回退移除了该条目，之后再次读取可能重新加载；
  • 已加载的嵌套文件被修改不会自动感知，需要新会话。

#更新行为

修改全局或向上发现的 AGENTS.md 时，OpenCode 会在下一次模型请求前加入“指令更新”，不需要重启。

删除所有环境 AGENTS.md 会告知会话“之前的指令不再适用”。临时读取失败会保留上次内容，不会误判为删除。

#写得好的 AGENTS.md

建议包含：

  1. 构建/测试/类型检查命令；
  2. 目录职责与边界；
  3. 代码风格与命名约定；
  4. 禁止事项（生成文件、密钥、危险命令）；
  5. 验证要求（提交前必须跑什么）；
  6. 评审偏好（输出格式、严重程度）。

避免：

  • 大段复制框架文档；
  • 与代码无关的公司介绍；
  • 互相矛盾的规则；
  • 过长的背景故事。

模板：

# AGENTS.md

## Commands
- Install: `bun install`
- Dev: `bun dev`
- Test: `bun test`
- Typecheck: `bun typecheck`
- Lint: `bun lint`

## Architecture
- `src/api`：HTTP 入口，不写业务逻辑
- `src/core`：领域逻辑
- `src/db`：数据库访问
- `src/web`：前端

## Conventions
- 使用 TypeScript strict。
- 新函数必须有单元测试。
- 错误用 `Result`，不要抛裸字符串。

## Do not
- 不编辑 `dist/`、`generated/`。
- 不提交 `.env`。
- 不执行 `git push`。

## Review
- 先列 bug，再列建议。
- 每条附文件与行号。

#9.3 instructions：追加指令文件

除了 AGENTS.md，还可以显式列出文件、glob 或 URL：

{
  "$schema": "https://opencode.ai/config.json",
  "instructions": [
    "CONTRIBUTING.md",
    "docs/guidelines/*.md",
    "~/rules/opencode.md",
    "https://example.com/instructions.md"
  ]
}

规则：

  • 在 AGENTS.md 之后加载，按数组顺序；
  • 多份配置的条目会合并；
  • 相对路径从工作目录向上到项目根查找；
  • 本地文件变更会像 AGENTS.md 一样更新；
  • 缺失文件跳过；URL 拉取失败跳过或保留上次内容；
  • URL 拉取超时 5 秒。

适合：

  • 复用 CONTRIBUTING.md；
  • 公司统一规范；
  • 远程维护的规则文档。

#9.4 References：把外部目录/仓库挂进来

{
  "references": {
    "docs": {
      "path": "../product-docs",
      "description": "产品行为与术语"
    },
    "effect": {
      "repository": "Effect-TS/effect",
      "branch": "main"
    }
  }
}

本地路径：

  • 相对路径从配置文件所在目录解析；
  • 支持绝对路径和 ~/；
  • 简写字符串只有在以 .、/、~ 开头时才当本地路径。docs 会被当作 Git 仓库，应写 ./docs。

Git 仓库：

  • 支持 owner/repo、Git URL、host/path、SCP 形式；
  • 不支持本地 file: 仓库；
  • 不写 branch 时跟随默认分支；
  • 缓存在全局数据目录，例如：
~/.local/share/opencode/repos/github.com/Effect-TS/effect

刷新：

  • 引用加载或重载时后台检查；
  • 每个 Location 有新提示时后台检查；
  • 上次尝试超过 24 小时才刷新；
  • 克隆/刷新不阻塞提示；
  • 缓存可能在使用中被更新，不要编辑缓存目录。

description 会告诉 Agent 何时使用；没有描述仍可用，但不会自动宣传。

注意：References 不授予额外权限。访问外部路径仍受 external_directory、read、edit 规则约束。

#9.5 Compaction：上下文压缩

默认开启：

{
  "compaction": {
    "auto": true,
    "keep": { "tokens": 15000 },
    "buffer": 20000
  }
}
字段默认行为
autotrue接近上限时自动压缩；被 Provider 判超长时恢复一次
keep.tokens15000摘要旁保留的近期原文 token 数
buffer上限的 15%，至少 16k离模型上限预留的空间；越大越早压缩

压缩过程：

之前：[系统提示][较早对话][最近 15k][待处理]
请求：[系统提示][较早对话][最近 15k][摘要指令]
之后：[系统提示][摘要][最近 15k][待处理]

摘要包含：

  • 目标与要求；
  • 决策；
  • 已完成/进行中工作；
  • 阻塞与下一步；
  • 相关文件。

压缩有损。细节重要时：

  • 提前 /compact；
  • 增大 keep.tokens；
  • 把关键结论写进 AGENTS.md 或文件；
  • 拆分会话。

手动压缩：

opencode api post /api/session/ses_xxx/compact --data '{}'

后台压缩（实验性）：

{
  "experimental": { "background_compaction": true }
}

在阈值前预生成摘要，减少停顿，但可能产生未使用的摘要成本。

#9.6 上下文分层策略

推荐把信息分成四层：

层内容生命周期
常驻AGENTS.md、核心规范始终
项目instructions、References 描述项目内
任务当前提示、附件、选中的技能单次任务
临时/btw、探索性工具输出不进入历史

实践：

  • 长期规则放 AGENTS.md；
  • 只在某些任务用的流程放 Skill；
  • 大块外部文档放 Reference，按需读取；
  • 一次性问题用 /btw；
  • 长任务定期总结到文件，而不是全靠对话记忆。

#9.7 工具输出也会占上下文

读取大文件、跑测试、MCP 返回大 JSON，都会消耗 token。可用 tool_output 限制：

{
  "tool_output": {
    "max_lines": 2000,
    "max_bytes": 51200
  }
}

模型仍可分段读取，但单次结果不会无限膨胀。

#9.8 常见上下文问题

现象可能原因处理
模型忘了前面的决定压缩或历史被截断把决定写入文件/AGENTS.md，或增大 keep
回答变慢、变贵上下文过大、工具输出过多/compact、限制输出、拆会话
规则不生效AGENTS.md 位置不对/被覆盖检查加载顺序与文件内容
嵌套规则没加载尚未读到该目录先让 Agent 读取该区域，或放到根文件
修改 AGENTS.md 不生效嵌套文件已加载不自动感知开新会话
Reference 读不到权限/路径/尚未克隆检查 external_directory 和缓存

#9.9 本章练习

  1. 给当前项目写一份 20 行以内的 AGENTS.md，包含命令、架构、禁止项。
  2. 用 instructions 引入 CONTRIBUTING.md。
  3. 配一个本地 Reference 和一个 Git Reference，观察描述是否出现在 Agent 行为中。
  4. 把 keep.tokens 从 15000 改到 30000，比较长会话的细节保留。
  5. 用 tool_output 限制测试输出，观察上下文占用变化。

#9.10 小结

  • 上下文按固定顺序组装，AGENTS.md 是常驻指令。
  • 嵌套 AGENTS.md 按需加载，修改后不一定立即生效。
  • instructions 适合复用现有规范，References 适合外部资料。
  • 压缩有损，关键结论要落到文件。
  • 控制工具输出与任务范围，比单纯换大模型更有效。

#10.6 Shell 注入

用 ! + 反引号插入命令输出：

  • 在活动项目目录、用配置的 Shell 执行；

  • 输出合并后插入；
  • 在 Agent 工具权限流程 之外 执行。

#10.8 执行与模型选择

命令先展开参数和 Shell 块，再作为用户提示提交。默认在当前会话执行。

模型优先级：

  1. 命令的 model；
  2. 否则命令 Agent 配置的模型；
  3. 否则当前会话模型。

示例：

---
agent: plan
model: openai/gpt-6.1-sol#high
---

设计 $ARGUMENTS 的实施方案。

/design migration 会先切到 plan，再提交提示。

#10.9 后台子任务

---
description: 审计改动
agent: general
subagent: true
---

审计 $ARGUMENTS 的 bug 和缺失测试。

行为：

值行为
true总是用子会话，即使 Agent 是 primary
false总是用当前会话，即使 Agent 是 subagent
省略仅当 Agent 是 subagent 时用子会话

子会话模型顺序：命令模型 → Agent 模型 → 父会话模型。

父会话保持可用，子任务完成后结果或失败会回传。

#10.10 加载与覆盖

Markdown 和 JSON 命令共享一个注册表，后加载的同名命令替换先加载的：

~/.config/opencode/commands/review.md   较低
.opencode/commands/review.md            覆盖全局

优先级：

  • 项目 > 全局；
  • 更近的项目目录 > 更外层；
  • 自定义可以替换内置命令。

保存文件后自动重载，不需要重启。

#第 11 章 Skills 技能系统

本章目标：用 SKILL.md 封装可复用的工作流，理解发现规则、ID、权限与按需加载。

#11.1 Skill 是什么

Skill 是“某类任务的做法说明”，只在需要时加载，避免把全部流程塞进每一轮提示。

一个 Skill 可以包含：

  • 触发条件（description）；
  • 工作流步骤；
  • 脚本、模板、参考资料；
  • 权限要求。

与命令的区别：

  • 命令由用户显式 /调用，通常是参数化提示；
  • Skill由模型按描述自动判断是否加载，也可以 @skill-id 显式加载。

#11.2 目录结构

推荐目录形式：

.opencode/skills/
└── git-release/
    ├── SKILL.md
    ├── scripts/
    │   └── changelog.ts
    └── references/
        └── release-policy.md

SKILL.md：

---
name: Git Release
description: 准备发布说明、版本号与 GitHub Release
---

## 工作流

1. 阅读 `references/release-policy.md`。
2. 汇总上一个标签以来的合并改动。
3. 先提出建议版本号，等用户确认。
4. 用户确认后才运行 `scripts/changelog.ts`。

Skill 内的相对路径以 SKILL.md 所在目录为基准。

#11.3 自动发现位置

范围位置
全局~/.config/opencode/skills
全局兼容~/.claude/skills、~/.agents/skills
项目.opencode/skills
项目兼容.claude/skills、.agents/skills

项目来源会从当前目录向上搜索到项目根，每一层都包含。

支持两种形式：

skills/
├── review.md
└── git-release/
    └── SKILL.md

规则：

  • 源根下的 *.md 是一个 Skill；
  • 精确命名为 SKILL.md 的文件可以嵌套在分组目录中；
  • 一个包含 SKILL.md 的目录就是一个 Skill，不再向内搜索；
  • 跳过隐藏文件/目录和 node_modules；
  • 最多向下搜索六层。

{
  "$schema": "https://opencode.ai/config.json",
  "skills": [
    "./team-skills",
    "~/shared/opencode-skills",
    "/opt/company-skills",
    "https://example.com/opencode/skills/"
  ]
}
值解析

~/用户主目录
绝对路径原样
HTTP(S)作为 HTTP 目录加载

多份配置的 skills 数组合并，不替换。

#11.5 Frontmatter

---
name: Git Release
description: 准备仓库发布
metadata:
  opencode/autoinvoke: false
---

...
字段行为
name显示名，默认用路径 ID
description展示给模型的摘要；没有描述就不会被自动宣传
metadata.opencode/autoinvokefalse 时从模型可用列表隐藏
disable-model-invocationtrue 等同于上一条

autoinvoke: false 只是隐藏，Skill 仍注册，仍可显式按 ID 加载。

V2 接受 license、compatibility 等可移植字段，但不解释它们。

#11.6 ID 规则

ID 由路径决定，name 只是显示名：

文件ID
&lt;source&gt;/git-release.mdgit-release
&lt;source&gt;/git-release/SKILL.mdgit-release
&lt;source&gt;/teams/release/SKILL.mdrelease
  • 精确、大小写敏感；
  • 可移植 Skill 建议用小写 kebab-case，1–64 字符；
  • V2 当前不强制该模式，也不强制 name 与目录一致。

#11.7 优先级

按 ID 选择，后注册的来源覆盖先注册的：

~/.config/opencode/skills/git-release/SKILL.md   较低
.opencode/skills/git-release/SKILL.md            实际加载

注册顺序（低 → 高）：

  1. 内置 Skill；
  2. .claude/skills（全局，再由远到近）；
  3. .agents/skills（同上）；
  4. ~/.config/opencode/skills；
  5. 项目 .opencode/skills（从项目根到当前目录）；
  6. 显式 skills 配置条目（按配置优先级和数组顺序）。

除非有意覆盖，避免重复 ID。

#11.8 加载过程

每个模型步骤，OpenCode 会列出：

  • 有权限的；
  • 有 description 的；
  • 未设置 autoinvoke: false 的 Skill。

列表只包含 ID、名称、描述，不包含正文。

模型调用 skill 工具：

{ "id": "git-release" }

然后 OpenCode：

  1. 选择当前 ID 的定义；
  2. 检查 Agent 的 skill 权限；
  3. 把正文（不含 frontmatter）加入对话；
  4. 提供 Skill 根目录和最多 10 个支持文件路径示例。

支持文件不会自动加载，Agent 需要按正文指引去读。

显式加载：在提示里写 @skill-id。

#11.9 权限

{
  "permissions": [
    { "action": "skill", "resource": "*", "effect": "allow" },
    { "action": "skill", "resource": "internal-*", "effect": "deny" },
    { "action": "skill", "resource": "experimental-*", "effect": "ask" }
  ]
}
效果行为
allow宣传并加载，无需审批
ask宣传，加载前询问
deny对模型隐藏，并拒绝加载

放到 agents.&lt;id&gt;.permissions 下可只对某个 Agent 生效。

#11.10 HTTP 目录

index.json：

{
  "skills": [
    {
      "name": "git-release",
      "version": "3",
      "files": ["git-release.md", "references/release-policy.md"]
    }
  ]
}

文件从 &lt;base-url&gt;/git-release/&lt;file&gt; 下载。

要求：

  • 路径安全、相对、同源；
  • 必须包含 SKILL.md 或 &lt;name&gt;.md；
  • 文件变化时递增 version，否则缓存不刷新。

#把脚本放旁边

#11.12 调试 Skill

按顺序检查：

  1. 文件是根级 *.md 还是嵌套 SKILL.md；
  2. 用路径 ID，不要用 name；
  3. 是否有 description；
  4. 是否 autoinvoke: false；
  5. Agent 的 skill 权限；
  6. 是否有更高优先级来源覆盖了同 ID；
  7. HTTP 目录的 index.json、同源路径和 version。

  3. 用权限禁止 internal-*，确认模型看不到。
  4. 用 @skill-id 显式加载一个 autoinvoke: false 的 Skill。
  5. 设计一个发布 Skill 的完整目录结构。

#11.14 小结

  • Skill 是按需加载的工作流，不是常驻提示。
  • 目录形式更适合带脚本和参考资料。
  • ID 由路径决定，优先级后注册覆盖先注册。
  • 权限控制可见性与加载。
  • 好的 Skill = 明确触发 + 可执行步骤 + 必要资源 + 最小权限。

#第 12 章 MCP 集成

本章目标：把 Model Context Protocol 服务接入 OpenCode，理解本地/远程、OAuth、Code Mode、权限与故障排查。

#12.1 MCP 能带来什么

MCP（Model Context Protocol）服务可以暴露：

  • Tools：可调用的函数；
  • Prompts：可变成斜杠命令的模板；
  • Resources：可读的文档、记录、数据；
  • Instructions：服务初始化时给模型的指引。

典型用途：

  • 文档检索（Context7）；
  • 项目/工单系统（Linear、Sentry、GitHub）；
  • 数据库、浏览器、设计稿；
  • 内部平台 API。

MCP 工具会占用模型上下文，只加需要的服务。

#12.2 用 CLI 添加

远程：

opencode mcp add context7 --url https://mcp.context7.com/mcp
opencode mcp list

本地：

opencode mcp add everything -- npx -y @modelcontextprotocol/server-everything

带环境变量：

opencode mcp add everything --env LOG_LEVEL=info -- npx -y @modelcontextprotocol/server-everything

全局：

opencode mcp add context7 --global --url https://mcp.context7.com/mcp

--global 写入全局配置；不加则写入当前项目配置。

#12.3 配置结构

{

      "my-server": {
        "type": "local",
        "command": ["npx", "-y", "example-mcp-server"]
      }
    }
  }
}

禁用但不删除：

{

    "servers": {
      "my-server": {
        "type": "local",

      }
    }
  }
}

V2 用 disabled，不是 enabled。

#12.4 本地服务

{
  "mcp": {
    "servers": {
      "everything": {
        "type": "local",
        "command": ["npx", "-y", "@modelcontextprotocol/server-everything"],
        "cwd": ".",
        "environment": {
          "LOG_LEVEL": "info",
          "MCP_API_KEY": "{env:MCP_API_KEY}"
        }
      }
    }
  }
}
字段必填说明
type是"local"
command是可执行文件 + 参数
cwd否工作目录，默认工作区
environment否追加到继承环境
disabled否为 true 时不连接
codemode否false 时直接暴露工具；默认 true
timeout否覆盖全局超时
protocol否legacy、auto、2026-07-28

环境变量用 {env:NAME}，不要写 $NAME，JSON 字符串不会展开 Shell 变量。

#12.5 远程服务

{
  "mcp": {
    "servers": {
      "context7": {
        "type": "remote",
        "url": "https://mcp.context7.com/mcp",
        "headers": {
          "CONTEXT7_API_KEY": "{env:CONTEXT7_API_KEY}"
        }
      }
    }

}
字段必填说明
type是"remote"
url是绝对 Streamable HTTP 端点
headers否请求头
oauth否OAuth 配置，或 false 关闭
disabled否不连接
codemode否默认 true
timeout否覆盖全局
protocol否协议版本

  "url": "https://mcp.example.com/mcp",
  "oauth": false,

}

#12.6 OAuth

远程服务默认启用 OAuth。需要登录时：

/mcps

选择服务并完成浏览器授权。CLI 也可发起：

opencode mcp auth sentry
opencode mcp logout sentry

客户端注册顺序：

  1. 配置了 oauth.client_id → 预注册客户端；
  2. 授权服务器支持 CIMD 且未设 redirect_uri → 使用元数据文档；
  3. 否则动态客户端注册（DCR）。

预注册客户端：

{
  "mcp": {
    "servers": {
      "company-tools": {
        "type": "remote",
        "url": "https://mcp.example.com/mcp",
        "oauth": {
          "client_id": "{env:MCP_CLIENT_ID}",
          "client_secret": "{env:MCP_CLIENT_SECRET}",
          "scope": "tools:read tools:execute",
          "callback_port": 19876,
          "redirect_uri": "http://127.0.0.1:19876/callback"
        }
      }
    }
  }
}

OAuth 字段使用 snake_case：

  • clientId → client_id
  • clientSecret → client_secret
  • callbackPort → callback_port
  • redirectUri → redirect_uri

凭据存储在配置之外，不要手动写入项目文件。

#12.8 协议版本

{
  "mcp": {
    "servers": {
      "modern": {
        "type": "remote",

值行为

auto先用 server/discover 探测 2026-07-28，不支持则回退

auto 对旧本地服务可能多起一个短命进程，并等待启动超时；只对确实需要新协议的服务开启。

#12.9 Code Mode

默认 codemode: true，MCP 工具通过 Code Mode 分组暴露：

tools.context_7.resolve_library_id(...)

好处：

  • 减少原生工具列表膨胀；
  • 便于组合调用；
  • 统一权限入口 execute。

需要工具出现在 Provider 原生工具列表时：

{
  "mcp": {
    "servers": {
      "context7": {
        "type": "remote",
        "url": "https://mcp.context7.com/mcp",
        "codemode": false
      }
    }
  }
}

#12.10 命名规则

工具名为 &lt;server&gt;_&lt;tool&gt;，非字母、数字、_、- 的字符替换为 _：

server: context 7
tool:   resolve.library/id
name:   context_7_resolve_library_id

MCP 提示变成命令 &lt;server&gt;:&lt;prompt&gt;：

/context_7:find_docs react "server components"

服务名要短且唯一，避免规范化后冲突。

#12.11 权限

按规范化工具名匹配：

{
  "permissions": [
    { "action": "context7_*", "resource": "*", "effect": "deny" }
  ]
}

资源读取工具：

ActionResource

opencode_read_mcp_resource&lt;server&gt;:&lt;uri&gt;
{
  "permissions": [
    {
      "action": "opencode_read_mcp_resource",
      "resource": "docs:*",
      "effect": "allow"
    }
  ]
}

如果 Agent 拒绝某服务的所有工具，或拒绝 Code Mode 的 execute，该服务的 instructions 也会被省略。

#12.12 服务指令与输入请求

服务初始化返回的 instructions 会加入系统提示：

<mcp_instructions>
  <server name="sentry">
    创建新问题前先搜索是否已存在。
  </server>
</mcp_instructions>

服务在调用中请求输入时，OpenCode 显示表单或链接；关闭表单即取消请求。

#12.13 管理

opencode mcp list
opencode mcp auth
opencode mcp auth sentry
opencode mcp logout sentry

TUI 中 /mcps 可查看、连接、断开、认证。

断开连接不会修改配置；要持久禁用，编辑配置里的 disabled。删除服务则删除对应配置项。

#12.14 安全建议

  1. 最小化服务：每多一个服务就多一组工具和上下文。
  2. 最小权限：按工具名拒绝不需要的能力。
  3. 密钥走环境变量：不要写进仓库。
  4. 审查远程服务：它会收到你的查询和工具参数。
  5. 注意会话 ID 元数据：OpenCode 会在 _meta["ai.opencode/sessionID"] 中传会话 ID，远程服务可能记录它。它不是认证凭据。
  6. 本地服务同样是代码：npx 拉取的包要在可信来源。

  4. 为一个远程服务配置 OAuth 并登录。
  5. 把 codemode 设为 false，对比工具暴露方式。

#12.18 小结

  • MCP 服务提供工具、提示、资源和指令。
  • V2 配置在 mcp.servers，用 disabled 而不是 enabled。
  • 远程默认 OAuth，本地用 stdio 命令。
  • Code Mode 默认开启，按需关闭。
  • 工具名会规范化，权限按规范化名称匹配。
  • 服务越多，上下文与攻击面越大，保持最小化。

#第 13 章 插件系统

本章目标：理解 V2 插件的部件、加载方式与管理命令；能配置现成插件，并为第 19 章开发插件打基础。

#13.1 插件能做什么

插件可以：

  • 注册工具、命令、Agent、Skill、MCP 服务；
  • 修改 Provider、Model、Reference；
  • 拦截提示、模型请求、HTTP 请求/响应；
  • 增加 TUI 命令、路由、渲染器；
  • 给 Desktop 加面板、命令、设置页；
  • 定义 RPC，供其他部件或客户端调用。

插件运行在 OpenCode 服务进程内，能力很大，风险也大。只安装可信插件。

#13.2 配置

{
  "$schema": "https://opencode.ai/config.json",
  "plugins": [
    "opencode-acme-plugin",
    "opencode-acme-plugin@1.2.0",
    "@acme/opencode-plugin",
    "./plugins/local",
    "../shared/plugin",
    "/absolute/path/plugin",
    "file:///home/me/plugins/local",
    {
      "package": "@acme/opencode-plugin",
      "options": {
        "agent": "reviewer",
        "strict": true
      }
    }
  ]
}

要点：

  • 相对路径从包含该条目的配置文件目录解析。
  • 本地路径必须是 目录，指向单个文件会被跳过。
  • 多份配置的 plugins 数组按优先级合并，不是替换。
  • plugins 数组按顺序处理。

#13.3 自动发现

.opencode/
└── plugins/
    ├── concise.ts
    ├── reviewer.js
    └── acme-package/

OpenCode 会自动加载每个 .opencode/plugins/ 下的：

  • 直接的 .ts / .js 文件；
  • 直接的插件包目录。

全局：

~/.config/opencode/plugins/

注意：项目根 opencode.json 旁边的 plugins/ 不会 自动发现，需要显式配置：

{
  "plugins": ["./plugins/local"]
}

#13.4 启用与禁用

{
  "plugins": ["*", "-opencode.provider.*", "opencode.provider.openai", "-acme.reviewer"]
}

规则：

  • - 前缀禁用；
  • * 表示所有插件；
  • .* 匹配某个 ID 前缀；
  • 后面的 ID 可以重新启用。
  • 两个内置插件不能被移除：opencode.config.policy 和 opencode.provider.opencode，否则仓库可以绕过组织策略。

#13.5 CLI 管理

opencode plugin add opencode-acme-plugin@1.2.0
opencode plugin list
opencode plugin list --builtin
opencode plugin check
opencode plugin update
opencode plugin update opencode-acme-plugin
opencode plugin remove opencode-acme-plugin@1.2.0

支持：

  • npm 名称、版本、tag、范围；
  • npm 兼容的 Git 包；
  • GitHub 简写、HTTPS、SSH；
  • 私有仓库（用现有 Git 凭据）；
  • ::path: 子目录选择器。
opencode plugin add github:acme/opencode-plugin
opencode plugin add git+ssh://git@github.com/acme/opencode-plugin.git#main
opencode plugin add 'github:acme/plugins#main::path:packages/opencode-plugin'

plugin add 不接受 tarball 和 npm alias。

plugin check 检查服务端、GUI、TUI 包插件的更新；plugin update 更新所有过期包。本地插件和精确版本会跳过。

#13.6 四种部件

一个插件包可以包含任意组合：

{
  "name": "opencode-acme-plugin",
  "version": "1.0.0",
  "type": "module",
  "exports": {
    ".": "./src/index.ts",
    "./tui": "./src/tui.tsx",
    "./gui-experimental": "./dist/gui-experimental.cjs",

  }
}
部件导出运行位置用途
Server. 或 ./server服务进程工具、Hook、集成、命令、Agent
TUI./tui终端客户端命令、路由、插槽、Markdown 渲染
GUI./gui-experimentalDesktop面板、命令、设置页
RPC./rpc契约服务端实现，其他部件/客户端调用

一个条目会加载插件的所有部件。只有 TUI 部件的包应放到 cli.json 的 plugins。

#13.7 最小服务端插件

#13.9 加载与重载

  • 配置目录下的变化会自动重载。
  • 服务启动时立即加载缓存的包插件，后台安装缺失包，并检查未固定版本的 npm/Git 插件。
  • 精确 npm 版本和完整 Git commit 保持固定。
  • 未被监听的本地依赖变化可能需要重启：

{
  "plugins": ["opencode-acme-plugin"]

TUI 专用插件放在 cli.json：

{
  "plugins": ["opencode-acme-cli"]

#13.11 什么时候该写插件

适合：

  • 接入内部 API（自定义工具）；
  • 统一注入请求头/租户信息；
  • 对提示或上下文做合规改写；
  • 动态注册 Provider/Model；
  • 给 Desktop 加内部面板；
  • 暴露 RPC 给内部平台。

不适合：

  • 只是重复提示 → 用命令或 Skill；
  • 只是项目规则 → 用 AGENTS.md；
  • 只是外部数据 → 先看 MCP；
  • 只是格式化 → 用 formatter。

#13.12 安全与运维

  1. 插件 = 服务进程内的任意代码，权限规则不能沙箱它。
  2. 固定版本或 commit，避免供应链漂移。
  3. 审查 postinstall、网络请求和文件访问。
  4. 生产环境禁用不必要插件。
  5. 用 plugin list 和日志确认实际加载的版本。
  6. 插件报错时先看服务日志，再尝试禁用排查。

#13.15 小结

  • V2 插件有 Server、TUI、GUI、RPC 四种部件。
  • 配置在 plugins，本地路径必须是目录。
  • 支持包、Git、本地目录和选项对象。

#第 14 章 快照、撤销与工作树

本章目标：安全地回退改动，用工作树隔离并行任务，并理解这些能力的边界。

#14.1 快照是什么

OpenCode 在每个模型步骤前后尝试捕获文件系统快照，用来支持 /undo 恢复文件。

模型步骤前 ── 快照 A
模型修改 src/api.ts
步骤结束 ── 快照 B ── 记录变更：src/api.ts

快照是 尽力而为：任一快照不可用，会话继续，但该步骤可能无法恢复文件。

#14.2 撤销流程

/undo

OpenCode：

  1. 暂存回滚；
  2. 恢复受影响文件；
  3. 把被撤销的提示放回输入框。

编辑后重新发送即确认回滚。发送前可：

/redo

取消暂存，恢复对话和文件。

快捷键（默认）：

操作快捷键
撤销Ctrl+X 然后 U
重做Ctrl+X 然后 R

也可以在消息上选择 Revert，回滚到某条消息。

#14.3 快照范围

只覆盖 会话活动目录 内、Git 工作树中的文件：

内容是否捕获
活动目录内已跟踪文件是
未忽略的未跟踪文件（单个 ≤ 2 MiB）是
Git 忽略的文件否
单个大于 2 MiB 的未跟踪文件否
活动目录外的文件否
Git 元数据、提交、分支、数据库、进程否

例如会话在 packages/app，只捕获该目录下的文件，不会恢复 packages/server 的改动。

没有 Git 仓库时，/undo 仍可回退对话，但不能恢复文件。

#14.4 恢复规则

回滚只恢复“所选边界之后、归属于助手步骤”的路径：

时间线src/api.tssrc/new.ts
选择边界版本 A不存在
后续步骤版本 B创建
回滚后版本 A删除

未被这些步骤改过的路径保持不动。

注意：

  • 当前对受影响路径的编辑可能被覆盖；
  • 回滚前先看 git diff；
  • 回滚不会撤销 Shell 对数据库、服务、网络、Git 提交、忽略文件的副作用；
  • 外部编辑器和命令仍可能在捕获与恢复之间改动工作树。

#14.5 存储与关闭

快照存在 OpenCode 数据目录下的独立 Git 对象库，不会创建提交、移动分支或改索引。

关闭：

{
  "snapshots": false
}

关闭只停止 未来 的捕获，不删除已有快照；对话回退仍可用，但没有文件状态可恢复。

#14.6 安全使用建议

  1. 重要工作先提交或备份。
  2. /undo 前看 git status 和 git diff。
  3. 不要把它当事务或备份。
  4. 大文件、生成目录、数据库不在保护范围。
  5. 回滚后重新跑测试，确认状态一致。

#14.7 工作树（Worktree）

工作树让你在同一仓库的多个目录并行工作，互不干扰。

OpenCode 默认使用 Git 工作树。创建时可指定名称，目录由配置决定：

{
  "worktree": {
    "directory": "../worktrees"
  }
}

规则：

  • 相对路径相对于项目的规范检出目录；
  • 全局和项目配置都适用；
  • 绝对路径原样使用；
  • ~/ 相对用户主目录；
  • 不配置时使用服务数据目录下的 worktree/&lt;项目 ID 前六位&gt;；
  • 修改配置不会移动已有工作树。

示例：每个项目自己的 .lane/trees/：

{
  "worktree": {
    "directory": ".lane/trees"
  }
}

#14.8 创建与管理

TUI 中可通过会话移动/工作树对话框操作：

操作默认键
新建工作树Ctrl+A（移动会话对话框内）
移动会话Ctrl+M
删除工作树Ctrl+D
刷新Ctrl+R
生成名称Tab

API：

opencode api get /api/worktree
opencode api post /api/worktree --data '{"projectID":"prj_xxx","name":"feature-a"}'
opencode api delete /api/worktree --data '{"projectID":"prj_xxx","directory":"/path/to/wt"}'
opencode api post /api/worktree/refresh --data '{"projectID":"prj_xxx"}'
上面的请求体是示意；字段名与必填项以当前运行服务的 /openapi.json 为准。

插件也可注册自己的工作树策略；注册后自动成为默认。创建失败不会回退到 Git。

#14.9 并行会话策略

推荐按“任务”而不是“文件”拆分会话：

会话 A：实现功能（工作树 A）
会话 B：写测试（工作树 B）
会话 C：代码评审（只读，主工作树）

好处：

  • 文件不冲突；
  • 每个会话上下文更聚焦；
  • 评审者能在稳定代码上工作。

注意：

  • 工作树仍共享同一个 Git 仓库对象；
  • 端口、数据库、缓存等外部资源要自己隔离；
  • 合并前统一跑测试；
  • 不要让两个 Agent 同时改同一工作树。

#14.10 会话移动

会话可以移动到另一个目录/工作树：

opencode api post /api/session/ses_xxx/move --data '{"directory":"/path/to/worktree"}'

或在 TUI 的移动会话对话框操作。

移动后：

  • 会话保留历史；
  • 指令状态会保留，目标目录的 AGENTS.md 以“更新”形式引入；
  • 相对路径与工具权限按新位置重新判断。

#14.11 回退与工作树组合

典型安全流程：

1. 在工作树 A 开新会话。
2. 实现并测试。
3. /diff 审查。
4. 不满意：/undo 逐步回退。
5. 满意：提交，合并回主分支。
6. 删除工作树。

如果工作树里已经提交：

  • /undo 不会回退提交；
  • 用 Git 回退；
  • 快照只覆盖文件状态，不覆盖 Git 历史。

#14.12 常见问题

现象原因处理
/undo 不恢复文件非 Git 仓库 / 文件在活动目录外 / 被忽略初始化 Git，或手动恢复
回滚后仍有改动Shell 副作用 / 未被归属的路径看 git diff，手动处理
工作树创建失败分支冲突、目录不可写、策略限制换名称/目录，看日志
会话移动后规则变化新目录的配置/权限不同检查目标目录配置
删除工作树失败有未提交改动先提交或显式 force

#14.13 本章练习

  1. 在 Git 仓库里让 Agent 改两个文件，用 /undo 回退一个步骤。
  2. 创建一个未跟踪的小文件，确认快照能恢复；再创建一个被 .gitignore 忽略的文件，确认不能。
  3. 配置 worktree.directory，创建一个工作树并在其中开会话。
  4. 把会话移动到工作树，确认历史保留。
  5. 删除工作树，观察未提交改动的处理。

#14.14 小结

  • 快照按模型步骤捕获，/undo 同时回退对话与文件。
  • 只在 Git 工作树、活动目录内生效，且有大小/忽略限制。
  • 快照不是备份，Shell 副作用不可回滚。
  • 工作树用于并行任务隔离，目录可配置。
  • 先提交、再回滚或合并，是最稳的习惯。

本章目标：让 Agent 获取实时信息、读取图片/PDF，并在代理与合规环境下稳定工作。

#15.1 Web 搜索

查找 Bun 最新版本并总结变化。

首次搜索会请求允许并选择提供商。OpenCode 内置五家：

FirecrawlfirecrawlFIRECRAWL_API_KEY

连接方式：

/connect

或启动前设置环境变量：

TAVILY_API_KEY=your-key opencode

#15.2 选择与限制

固定提供商：

{
  "websearch": {
    "provider": "tavily"
  }
}

自动选择：

{
  "websearch": {
    "provider": "random"
  }
}

行为：

  • 每个会话记住选中的提供商，直到被限流；
  • 返回 HTTP 429 时，random 会换一个可用提供商重试；
  • 被限流的提供商按 Retry-After 冷却，缺失时 60 秒；
  • 全部冷却时立即失败；
  • 移动会话或重启服务会清除会话记忆；
  • 同一工作区的冷却状态共享。

#15.3 搜索权限与关闭

{
  "permissions": [
    { "action": "websearch", "resource": "*", "effect": "ask" }
  ]
}

resource 是搜索查询，可以按关键词做精细控制。

彻底关闭：

{
  "websearch": false
}

这会从模型请求中移除搜索工具。

#15.4 Web Fetch

webfetch 是一个独立工具，按 URL 读取网页/文本。权限：

{
  "permissions": [
    { "action": "webfetch", "resource": "*", "effect": "ask" },
    { "action": "webfetch", "resource": "https://docs.example.com/*", "effect": "allow" }
  ]
}

注意：

  • URL 是资源，适合按域名放行；
  • 抓取内容可能包含不可信指令，模型应把它当数据而非命令；
  • 内网地址是否可达取决于服务进程网络；
  • 敏感页面不要交给不可信模型/提供商。

#15.5 附件：支持的类型

输入模型收到
UTF-8 文本文件名 + 解码文本
目录非递归的即时文件/目录列表
PNG / JPEG / GIF / WebP图片媒体
PDF文档媒体

其他：

  • SVG 按文本处理；
  • AVIF、BMP、音频、视频等二进制不会进入模型请求；
  • 不支持的二进制先转文本或转 PNG；
  • HTTP/HTTPS 附件 URL 不支持。

#15.6 附件语法

V2 的提示/命令输入用 uri、可选 name、description：

{
  "uri": "file:///home/me/project/src/server.ts",
  "name": "server.ts",
  "description": "HTTP 服务入口"
}

文本文件可选行范围：

file:///home/me/project/src/server.ts?start=20&end=60

内联数据：

{
  "uri": "data:text/plain;base64,SGVsbG8sIE9wZW5Db2RlIQ==",
  "name": "greeting.txt"
}

#15.7 附件限制

限制值

图片 Base64默认 5 MiB
图片尺寸默认 2000×2000

#15.8 图片处理

{
  "media": {
    "image": {
      "auto_resize": true,
      "max_width": 2000,
      "max_height": 2000,
      "max_base64_bytes": 5242880
    }
  }
}
字段默认行为
auto_resizetrue超限时等比缩放；false 时直接拒绝
max_width2000最大宽度
max_height2000最大高度
max_base64_bytes5242880Base64 后最大字节

auto_resize: true 时会尝试更小的 PNG/JPEG 编码，输出类型可能变化。若缩放器不可用，原图会原样传递——这些是处理限制，不是安全边界。

#15.9 使用多模态的建议

  1. 先确认模型支持图片/PDF 输入，否则会被拒绝或收到替代说明。
  2. 截图尽量裁剪到关键区域，减少 token。
  3. 架构图、UI 稿、错误截图比整页文档更有效。
  4. PDF 很大时先提取相关页。
  5. 不要把密钥、身份证件等敏感图片发给不可信提供商。
  6. 对图片中的文字，必要时让模型先 OCR 式复述，再推理。

#15.10 网络与代理

标准代理变量：

export HTTP_PROXY=http://proxy.example.com:8080
export HTTPS_PROXY=http://proxy.example.com:8080
export NO_PROXY=localhost,127.0.0.1,::1

关键：CLI 与后台服务之间走本地 HTTP，必须把 loopback 放进 NO_PROXY。

后台服务只在从该 Shell 启动时继承导出变量。要持久化：

opencode service set env HTTP_PROXY http://proxy.example.com:8080
opencode service set env HTTPS_PROXY http://proxy.example.com:8080
opencode service set env NO_PROXY localhost,127.0.0.1,::1
opencode service start

删除：

opencode service unset env HTTPS_PROXY

#15.11 代理认证与私有 CA

URL 内嵌凭据：

export HTTPS_PROXY='http://user:p%40ssword@proxy.example.com:8080'

特殊字符要百分号编码。持久化后 service get env 会显示完整 URL，注意不要泄露。

私有 CA：

export NODE_EXTRA_CA_CERTS=/etc/company/ca.pem

后台服务：

opencode service set env NODE_EXTRA_CA_CERTS /etc/company/ca.pem
opencode service start

#15.12 前台服务

--standalone 和 serve 使用自己进程的环境，service set env 不影响它们：

HTTPS_PROXY=http://proxy.example.com:8080 \
NO_PROXY=localhost,127.0.0.1,::1 \
opencode --standalone

#15.14 模型预热（Warming）

长会话首次请求可能较慢。可选预热：

{
  "warming": {
    "prompt": "Do not perform any work. Reply with exactly: OK",
    "interval": "4 minutes",
    "duration": "30 minutes"
  }
}

默认关闭。开启后会周期性发送瞬态请求，保持最近活跃模型会话温暖。

成本提醒：

  • 每次预热都计费；
  • 只对支持的 Provider/路由有效；
  • 短会话不值得开；
  • 生产环境先做成本评估。

#第 16 章 Server API 与客户端

#16.5 创建会话并发送提示

curl -u opencode:secret ...

#16.6 @opencode/client

安装：

bun add @opencode/client

创建客户端：

import { OpenCode } from "@opencode/client"

const client = OpenCode.make({
  baseUrl: "http://localhost:4096",
  // 直连服务用 Basic；若经自建网关，可按网关要求改成 Bearer。
  headers: {
    authorization: `Bearer ${process.env.OPENCODE_TOKEN}`,
  },
})

const session = await client.session.create({
  location: { directory: "/workspace" },
})

await client.session.prompt({
  sessionID: session.id,
  text: "审查当前改动",
})

每个操作最后一个参数可传 AbortSignal 或请求头：

await client.session.list(undefined, {
  signal: AbortSignal.timeout(10_000),
})

#16.7 事件流

for await (const event of client.event.subscribe()) {
  console.log(event.type)
}

要点：

  • 事件连接是惰性的：创建客户端/迭代器不连接，开始消费才连接；
  • 每个客户端共享一条事件连接；
  • 取消某个订阅只影响该迭代器，最后一个订阅者离开才关闭连接；
  • 共享源会等待活跃订阅者处理事件，慢消费者应自行缓冲；
  • 订阅是实时的，不重放、不自动重连；
  • 断线后需要重新订阅；
  • 新订阅者会收到当前 server.connected 标记，而不是历史业务事件。

按类型过滤：

for await (const event of client.event.subscribe({
  types: ["config.updated"],
})) {
  // event.type 为 "config.updated" | "server.connected"
}

server.connected 总会通过，便于重新同步。

#16.8 本地服务发现

Node 环境：

import { OpenCode } from "@opencode/client"
import { Service } from "@opencode/client/service"

const endpoint = await Service.ensure()
const client = OpenCode.make({
  baseUrl: endpoint.url,
  headers: Service.headers(endpoint),
})

const info = await client.server.info()

方法：

  • Service.discover()：返回健康端点，不启动进程；
  • Service.ensure()：必要时启动兼容服务；
  • Service.stop()：停止已注册服务；
  • Service.headers(endpoint)：生成认证头。
const endpoint = await Service.ensure({
  version: (v) => v.startsWith("2."),
  command: ["opencode", "serve", "--service"],
  onStart(reason, previousVersion) {
    console.log(reason, previousVersion)
  },
})

#16.9 插件 RPC

服务端插件可以定义带类型的 RPC，客户端导入契约后调用：

import { OpenCode } from "@opencode/client"
import { Acme } from "opencode-acme-plugin/rpc"

const client = OpenCode.make({ baseUrl: "http://localhost:4096" })
const acme = client.rpc(Acme)
const result = await acme.search(
  { query: "hello" },
  { location: { directory: "/workspace" }, signal: AbortSignal.timeout(10_000) },
)

订阅：

const unsubscribe = acme.events.on("updated", (event) => {
  console.log(event.type, event.location.directory, event.data.text)
})

通用 HTTP 调用：

POST /api/rpc/{rpcID}/{method}
{ "input": ... }
→ { "output": ... }

注意：

  • 导入契约不会注册插件；服务端必须已配置并实现该 RPC；
  • RPC 订阅按本地名称跨所有 Location 接收事件，需要自己按 event.location 过滤；
  • Promise 客户端不本地执行 Schema 解析，服务端返回已解析结果。

#16.10 权限与审批 API

待审批：

opencode api get /api/permission/request

会话级：

opencode api get /api/session/ses_xxx/permission
opencode api post /api/session/ses_xxx/permission/<requestID>/reply \
  --data '{"decision":"once"}'

decision 可选：once、always、reject。

非交互客户端必须处理审批；否则 Agent 可能卡住。生产集成建议：

  • 预配置 allow / deny，减少运行时审批；
  • 或在平台侧实现审批 UI；
  • 永远保留 deny。

#16.11 文件与工作区

opencode api get /api/fs/list?path=.
opencode api get '/api/fs/read/src/index.ts'
opencode api get /api/vcs/status
opencode api get /api/worktree

文件 API 有独立的路径与权限约束；不要假设它能绕过 Agent 权限。

#16.12 错误处理

常见错误：

状态含义
400参数/Schema 不合法
401认证失败
403策略/权限拒绝
404会话/资源不存在
409冲突（如重复 ID）
503服务不可用/未就绪

建议：

  • 用生成的类型，不要手写猜测字段；
  • 对 401/503 做重试与退避；
  • 对 403 不要盲目重试，检查 policies；
  • 记录请求 ID / 会话 ID 便于排查。

#16.13 安全

  1. 不要把服务暴露到公网而不设密码。
  2. 用反向代理 + TLS + 额外认证。
  3. CORS 只放行可信来源。
  4. API 能改配置、跑工具，等同高权限操作。
  5. 日志和事件可能包含提示、文件内容、密钥，谨慎采集。
  6. 插件 RPC 的输入输出也要校验，别信任调用方。

#16.14 本章练习

  1. 用 opencode api 创建会话并发送提示。
  2. 用 client.session.list() 列出会话。
  3. 订阅 client.event.subscribe()，观察一轮对话的事件类型。
  4. 实现一个脚本：创建会话 → 发送审查提示 → 输出结果。
  5. 给服务设密码，用 Basic Auth 调用。
  6. 读取 /api/permission/request，模拟一次审批回复。

#16.15 小结

  • V2 API 是正式契约，OpenAPI 在 /openapi.json。
  • opencode api 适合本地调试，@opencode/client 适合应用集成。
  • 事件流实时、不重放，断线要重订。
  • 本地服务可用 Service.ensure() 发现/启动。
  • 认证、CORS、审批和日志都是安全边界。

#17.8 性能：先量后调

× 工具数量与输出
× 推理变体
× 网络/代理
× 压缩与重试

  4. 减少往返：清晰提示、明确验收标准；
  5. 优化网络：代理、就近端点、超时；
  6. 最后才考虑换更大上下文模型。

  5. 禁用不用的 MCP，比较请求延迟。
  6. 写一份团队排错清单。

#17.14 小结

  • 先分层：客户端、服务、项目。
  • service status + /api/info 是最快入口。
  • 日志按 role 和 run 过滤。
  • 性能优化优先级：上下文 → 工具 → 模型 → 网络。
  • 更新要固定版本、备份配置、逐步验证。

  id: "acme.tickets",

    await ctx.tool.transform((editor) => {
      editor.namespace({
        name: "acme",
        description: "Acme 工单工具",
      })

      editor.add({
        name: "create_ticket",
        description: "创建一个工单",
        input: {
          type: "object",
          properties: {
            title: { type: "string" },
            body: { type: "string" },
          },
          required: ["title"],
          additionalProperties: false,
        },
        options: { namespace: "acme", codemode: true },
        execute: async (input, context) => {

            signal: context.signal,

#19.7 Hook：拦截模型请求

await ctx.session.hook("context", (event) => {
  event.system.push({ type: "text", text: "只关注正确性与安全。" })
  delete event.tools.write
  event.options.temperature = 0.2
  event.options.maxTokens = 8000
})

Hook 类型：

  • context：Agent 主循环；
  • compaction：压缩摘要；

  • title：标题生成；
  • model.request：请求设置；
  • http.request / http.response：原生 HTTP。

规则：

  • options 每次模型调用从空开始；
  • Hook 按注册顺序运行，后者看到前者的修改；
  • 请求覆盖 > 模型默认 > 路由默认；
  • 置 undefined 是回退默认，不是删除配置；
  • 原始 HTTP body 覆盖在协议降级后应用。

execute: async (input, context) => {
  await ctx.permission.assert({
    sessionID: context.sessionID,
    agent: context.agent,

      search: async (input, context) => {
        const { query } = input as { query: string }
        const text = await findText(query, { signal: context.signal })
        if (!text) return context.error("not_found", "Not found", { query })
        return { text }
      },
    })

    await registration.events.emit("updated", { text: "ready" })
  },
})

客户端调用：

import { Acme } from "opencode-acme/rpc"

const client = OpenCode.make({ baseUrl: "http://localhost:4096" })
const acme = client.rpc(Acme)
const result = await acme.search({ query: "hello" })

原则：

  • 输入输出都要校验（JSON Schema 或 Standard Schema）；
  • 不要信任调用方；
  • 事件按 location 过滤；
  • 契约单独导出，避免客户端加载实现；
  • 事件数据必须是对象，标量/数组/null 不合法。

#第 20 章 V1 迁移与升级

本章目标：把 V1 的配置、Agent、命令、技能、插件和集成安全迁移到 V2，并知道如何验证与回滚。

#20.1 先说结论

  • V2 读取与 V1 相同的配置位置，大部分 V1 字段仍被接受。
  • 只有三处故意破坏：插件 API、Server API、终端客户端配置。
  • 转换到 V2 原生格式是 可选 的，不是能否运行的前提。
  • V1 与 V2 默认不再并存，且共用配置路径。不要用 V1 去读已经改成 V2 原生格式的文件。

推荐顺序：

1. 备份 V1 配置与 .opencode/
2. 安装 V2
3. 直接启动，验证模型/凭据/Agent/权限/MCP
4. 重写插件
5. 迁移 API 集成
6. 按需转换配置
7. 全量验证

#20.2 安装与卸载

V1 与 V2 使用同一个 opencode 命令，默认不再并存。

  • 包管理器安装的 V1：先卸载，再安装 V2。
  • curl 安装：V2 安装脚本会替换 V1 二进制。
  • Windows 包管理器（winget/Scoop/Chocolatey）不支持。
  • 可下载独立二进制。
opencode --version   # 应为 2.x

V2 读取：

/Library/Application Support/opencode/opencode.json(c)
/etc/opencode/opencode.json(c)
%ProgramData%\opencode\opencode.json(c)
~/.config/opencode/opencode.json(c)
<project>/opencode.json(c)
<project>/.opencode/opencode.json(c)

V2 在内存中规范化 V1 与 V2 字段，不重写源文件。支持的 V1 配置应继续工作。

#20.6 Agent 文件
