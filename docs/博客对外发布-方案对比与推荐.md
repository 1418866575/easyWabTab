# 博客对外发布：方案对比与推荐

> 目标：让自己在后台（本机/内网）写好的文章，能被其他人在博客前台看到。  
> 本文先盘点现状与真正的瓶颈，再给出三类方案，最后给出推荐路线。  
> 所有结论都基于当前代码（截至 master `810eb4c`），技术栈假设见文末。

---

## 0. 先说清楚：现在的瓶颈不是"前台没做"，而是"数据根本没出本机"

这是本文最重要的一节。如果跳过它直接谈方案，很容易做出与现状对不上的设计。

### 当前数据链路

```
作者在后台写文章
      ↓ 保存
作者自己浏览器的 IndexedDB（blog store，单文档 BlogData）
      ↓ markDirty + 防抖
blog.json 信封 → 作者自己的私有 WebDAV / 飞书多维表   ← 这一步是"跨设备同步"，不是"发布"
```

而前台（`/blog`、`/blog/article/:slug`）读的是：

```
访客打开 /blog
      ↓
BlogHomeView → useBlogStore() → 访客自己浏览器的 IndexedDB
```

**关键点**：`useBlogStore` 读的是**当前浏览器**的 IndexedDB。作者在自己电脑上写完文章，  
访客用自己电脑打开同一个网址，读到的是**访客自己那份空的 IndexedDB**——  
他看到的是空博客，而不是作者的文章。

所以"让别人看到"这个问题的本质不是"前台要不要加过滤"，而是：

> **把文章数据从「作者私有存储」搬到「访客能读到的地方」。**

### 现状盘点（哪些已经做好了）

| 能力             | 代码位置                                                                              | 状态              |
| -------------- | --------------------------------------------------------------------------------- | --------------- |
| 文章状态机          | `ARTICLE_STATUSES = draft/reviewing/published/offline/rejected`（types:1722）       | ✅ 已有            |
| 已发布过滤          | `listPublishedArticles()` = `status==='published' && !deletedAt`（blogCore:476）    | ✅ 已有            |
| 前台列表只出已发布      | `BlogHomeView.vue:26` `listPublishedArticles(store.articles)`                     | ✅ 已有            |
| 详情页防草稿泄露       | `BlogPostView.vue:57`，非已发布 → 404 回落                                               | ✅ 已有            |
| 发布前校验          | `collectPublishErrors()`（slug 唯一、分类/标签有效）                                         | ✅ 已有            |
| 状态流转           | `publishArticle/submitForReview/approve/reject/withdraw/offline`（blog store:285+） | ✅ 已有            |
| **静态导出纯函数**    | `buildBlogPublic()`（blogStaticExport.ts:60）只取已发布文章                                | ✅ 已有            |
| 静态导出 UI 入口     | `BlogSettingsPanel.vue:61` 调 `downloadBlogPublic()`                               | ✅ 已有            |
| 公网部署能力         | nginx serve `dist/` + Node 16718（`/api/` 反代），见 `nginx-easy-web-tab-site.conf`     | ✅ 已有            |

结论：**需求 1（发布状态）在数据和前台层面已经基本完成**；真正要新建的是"对外发布通道"，  
需求 3（多作者）是在此之上的增量。

## 1. 需求一：文章发布状态控制（草稿 / 已发布）

### 现状：基本已具备

状态机已覆盖 `draft → reviewing → published → offline`，且**草稿不外泄是"数据源头过滤"而非"前端隐藏"**  
——`listPublishedArticles` 在列表与详情两处都拦了一道，这是正确做法。

### 还需要补的 4 个点

| 缺口        | 说明                                 | 建议改动                                                                                  |
| --------- | ---------------------------------- | ------------------------------------------------------------------------------------- |
| 后台状态可见性   | 作者容易分不清"保存了"和"发布了"                 | 文章列表加状态列 + 过滤器（`filterArticles` 已支持 `status`）；编辑器顶部常驻状态徽标与"发布"主按钮                     |
| 预览未发布文章   | 发布前想看看前台效果                         | 后台加"预览"入口，走 `?preview=<id>` 绕过 `listPublishedArticles`（仅本机 IndexedDB 有该文章，天然只对作者可见）   |
| 定时发布 / 下线 | `publishedAt`/`offlineAt` 已有字段但无调度 | 静态方案下：构建时按 `publishedAt <= now` 过滤即可，"定时"退化成"下次构建生效"；动态方案下：查询条件加 `publishedAt <= now` |
| 发布前校验的可见性 | `collectPublishErrors` 已存在         | 发布失败时把 `errors[]` 逐条展示（现在只返回数组，需确认 UI 有展示）                                            |

### 一句话结论

> 需求 1 的工作重心**不在"加状态"，而在"让状态对作者可见、对访客不可绕过"**。  
> 对外发布时，务必保证过滤发生在**生成产物/服务端查询**那一层，而不是前端渲染时——  
> 前端过滤意味着草稿已经在访客的网络响应里了。

## 2. 需求二：把博客发布到公网，让外部访客可访问

下面三个方案的数据落点完全不同，对比如下：

| 维度            | A. 静态生成（SSG）           | B. 服务端 API + DB   | C. 云同步信封当发布通道                   |
| ------------- | ---------------------- | ----------------- | ------------------------------- |
| 文章数据落点        | `dist/` 里的静态 JSON/HTML | 服务端数据库            | 作者私有 WebDAV / 飞书                |
| 访客是否需要配置      | 否                      | 否                 | **是（要配同步源与凭证）**                 |
| 新增运维          | 无（nginx 已有）            | 有（DB、备份、鉴权）       | 无                               |
| 发布延迟          | 需重新构建部署                | 实时                | 近似实时                            |
| 阅读量 / 评论 / 搜索 | ❌（无服务端写入）              | ✅                 | ❌                               |
| SEO           | ✅（可再生成静态 HTML）         | ⚠️（SPA 需 SSR/预渲染） | ❌（SPA + 异步拉取）                   |
| 草稿安全性         | ✅ 导出时已过滤               | ✅ 查询条件过滤          | ❌ **全量信封含草稿 + 微信 appSecret 明文** |
| 与现有部署的契合度     | 最高（dist 已在传）           | 中（要扩 Node 服务）     | 低                               |
| 工作量           | 小（导出管道已建好）             | 大                 | 小但不可行                           |
| 适用规模          | 个人 / 小团队，数百篇内          | 多作者、高频更新、需互动      | 仅"自己多设备看"                       |

### 方案 A：静态站点生成（SSG）—— 把文章变成构建产物的一部分

**思路**：后台点"发布" → 生成一份只含已发布文章的数据文件 → 放进 `public/`，  
随 `vite build` 产出到 `dist/` → nginx 直接 serve → 前台改为 fetch 这些文件。

**实现步骤**：

1. **复用现成的 `buildBlogPublic()`**（纯函数，已过滤草稿、已把 `img:<id>` 还原为图片、含渲染后 HTML），  
   它产出的 `BlogPublic` 就是天然的接口契约，不用重新设计。
2. **落盘**：在后台"发布到站点"按钮里，除了现在的"下载 JSON"，再增加"写入项目"模式。  
   纯前端无法直接写 `public/`（构建期目录），所以有两种落法：
   - **A1 手工/CI 落盘**（零后端）：下载 JSON → 放进 `public/blog/` → `npm run build` → 上传 `dist/`。
   - **A2 落盘自动化**（推荐）：加一个构建期脚本 `scripts/gen-blog-public.cjs`，  
     由 Node 侧读取某个"导出快照"生成 `public/blog/*.json`；或反过来，  
     让后台把导出 POST 给 16718 的 Node 服务，由它写文件（`/api/blog/publish`）。
3. **产物粒度**（重要）：
   - 文章少（< 100 篇）：单文件 `public/blog/posts.json` 即可。
   - 文章多：**必须拆** `index.json`（列表用，只含 slug/title/excerpt/cover/作者/时间，**不含正文**）
     - `posts/<slug>.json`（详情页按需 fetch）。否则首屏要下几 MB。
4. **前台换数据源**：`BlogHomeView` / `BlogPostView` 从 `useBlogStore()` 改为读静态 JSON（见 §5 的"内容源抽象"）。
5. **部署**：`dist/` 上传 → nginx `try_files` 已有 SPA fallback，静态 JSON 按 `location ~* \.(json)$` 规则走即可  
   （注意：现有 nginx 对 `.json` 没设长期缓存，建议给 `/blog/*.json` 设 `Cache-Control: no-cache` 或短缓存，避免更新不及时）。

**优点**：零后端、零数据库、零新增运维；nginx 静态 serve 性能最好；草稿在**导出时就已剔除**，天然安全；  
SEO 友好（后续可再生成每篇静态 HTML）；完全贴合现有部署方式。

**缺点**：

- **发布 = 重新构建 + 上传 dist**，做不到"点一下立刻上线"（对周更/月更的个人博客可接受）。
- 无服务端写入 → 阅读量、评论、点赞都无法对访客持久化（现有 `viewCount` 是存在作者本地数据里的）。
- 多作者需要各自导出再合并（或统一由站长导出）。
- **图片是 data URL 内联**（`buildBlogPublic` 把 `img:<id>` 还原成 dataURL）→ 图多时 JSON 体积暴涨。  
  **建议改造**：导出时把图片写成 `public/blog/images/<id>.<ext>`，正文引用改为相对 URL。

### 方案 B：服务端 API + 数据库 —— 真正的动态博客

**思路**：给现有 Node 服务加一套博客读写 API，文章存数据库，前台改为调 API。

**实现步骤**：

1. **选型**：SQLite（单机最省事、零服务）或 MySQL（你已有经验）。数据量小、并发低时 SQLite 足够。
2. **扩服务**：在 `scripts/serve-with-rewrites.cjs`（16718，nginx 已反代 `/api/`）上加路由：
   - `GET  /api/blog/posts?page=&category=&tag=&author=` —— 只返回 `status='published' AND deletedAt IS NULL`
   - `GET  /api/blog/posts/:slug`
   - `POST /api/blog/posts/:id/view` —— 阅读量 +1
   - 后台写接口（`POST/PUT/DELETE /api/blog/admin/*`）**必须鉴权**（简单做法：一个 token + https）
3. **迁移**：把现有 IndexedDB 数据导成 `BlogPublic` JSON（`buildBlogPublic` 现成可用）→ 写个一次性导入脚本灌进 DB。
4. **后台改造**：编辑器保存时写 API（可先双写 IndexedDB + API，平滑过渡），保留现有离线编辑体验。
5. **前台换数据源**：同 §5 抽象，改成 `ApiSource`。

**优点**：访客零配置、发布实时、天然支持多作者与阅读量/评论/搜索、可加缓存与 CDN。

**缺点**：工作量最大；要处理鉴权、SQL 注入/参数化查询、备份、并发；现有"纯前端离线可用"特性会退化；  
多一个要运维的进程（不过 pm2 已在用，`pm2.config.cjs` 里加一项即可）。

### 方案 C：云同步信封当发布通道 —— 列出但**不推荐**

**思路**：把 `blog.json` 放到公共可读的 WebDAV / 飞书表，访客端配置"只读同步源"拉取。

**为什么不推荐（都是硬伤）**：

1. **安全问题致命**：信封是**全量**的，包含草稿、回收站文章，以及 **`BlogData.wechat.appSecret` 明文**  
   （types:1836，你之前明确选择明文存储）。下发到访客端 = 公众号凭证泄露。  
   要修就得在服务端做过滤，那就退化成方案 B 了。
2. **凭证要下发到访客端**：WebDAV 账号密码 / 飞书 token 得写进前端或让访客手动填，不可接受。
3. **SEO 为零**：SPA + 异步拉取，爬虫抓不到内容。
4. **性能**：全量信封数 MB，首屏白屏；飞书/WebDAV 还有速率限制。

**唯一适用场景**：你自己多台设备之间同步看（这正是它现在在做的事）。**不要用它对外发布。**

## 3. 需求三：多作者，前台按作者维度展示

### 现状

`BlogArticle.authorId?` 字段在（types:1743），但：

- 没有作者实体（无 `BlogAuthor`、无 `BlogData.authors`）——`authorId` 目前是个**没有落地的悬空字段**；
- 编辑器保存时 `input?.authorId`（blog store:193）来自调用方，没有来源；
- `BlogSettings.sessionTimeoutMin`（"本地作者身份过期分钟数"）只是个**本机会话**概念，不是真正的作者身份体系；
- 前台完全没有作者维度的展示与筛选。

5. `scripts/test-blog-core.ts` 的 `mkEnvelope` 补字段 + 加用例

## 4. 通用工程手法：先抽一个"内容源"接口

无论最终选 A 还是 B，**这一步都应该先做**。否则从 A 演进到 B 时，前台所有组件都要重写。

```ts
export interface BlogContentSource {
  listPosts(q: { page: number; pageSize: number; category?: string; tag?: string; author?: string; keyword?: string })
    : Promise<{ items: BlogPublicPost[]; total: number }>
  getPost(slug: string): Promise<BlogPublicPost | null>
  listAuthors(): Promise<BlogAuthorPublic[]>
  getAuthor(slug: string): Promise<BlogAuthorPublic | null>
}
```

三个实现：

| 实现                 | 用途             | 数据来源                                                             |
| ------------------ | -------------- | ---------------------------------------------------------------- |
| `IndexedDbSource`  | 本机预览 / 后台所见即所得 | 现有 `useBlogStore`（行为与今天完全一致）                                     |
| `StaticJsonSource` | 方案 A 对外        | `fetch('/blog/index.json')` + `fetch('/blog/posts/<slug>.json')` |
| `ApiSource`        | 方案 B 对外        | `fetch('/api/blog/posts?...')`                                   |

前台 `BlogHomeView` / `BlogPostView` 只依赖接口，切换实现只改一处注入。  
**这也让"后台看草稿、前台看已发布"两套视图天然分离**：后台继续走 `IndexedDbSource`（能看草稿），  
前台走对外源（只有已发布）。

## 5. 推荐方案

### 推荐：**方案 A（静态发布）起步 + 内容源抽象预留；需要动态能力时再升级到 B**

### 推荐理由

1. **与现有部署完全一致**：nginx 已在 serve `dist/`，`dist/` 本来就在传。方案 A 不新增任何进程、数据库或运维负担。
2. **工作量最小**：`buildBlogPublic()` 这个最难的部分**已经写好了**（纯函数、已过滤草稿、已还原图片、含渲染后 HTML，还有单测）。  
   剩下只是"把产物写成文件"+"前台换数据源"两件事。
3. **草稿安全性是结构性的**：过滤发生在**导出（构建）时**，草稿根本不会进入产物。  
   这比"前端过滤"或"下发全量再过滤"都可靠，也不会像方案 C 那样把 `appSecret` 一起泄露出去。
4. **性能与成本最优**：静态文件 + nginx，首屏快、可上 CDN、可生成静态 HTML 利于 SEO。
5. **演进路径干净**：先做内容源抽象，日后上方案 B 只换一个实现，前台零改动。
6. **契合实际使用频率**：个人/小团队博客多为周更、月更，"发布=构建部署"的延迟完全可以接受。

### 为什么不直接推荐 B

B 是"正确但重"的方案。它引入数据库、鉴权、备份、运维，而当前连作者实体都还没有——  
**在只有单作者、低频更新的阶段先上 B，是为尚未出现的需求预付成本**。  
等到真的需要"阅读量/评论/多作者实时协作"时再升级，那时内容源抽象已经就位，升级成本可控。

### 分阶段路线

| 阶段         | 内容                                                                                          | 依赖             |
| ---------- | ------------------------------------------------------------------------------------------- | -------------- |
| **P0**     | 发布状态可见性（列表状态列/过滤器、编辑器状态徽标、发布错误逐条提示、预览入口）                                                    | 无，基本是 UI 补齐    |
| **P1**     | **内容源抽象**（`BlogContentSource` 三实现 + 前台注入改造）                                                 | P0             |
| **P2**     | **静态发布链路**："发布到站点"按钮 → 产出 `index.json` + `posts/<slug>.json` → 落 `public/blog/` → 构建 → 前台读取 | P1             |
| **P3**     | **图片外置**：导出时图片写成独立文件、正文改相对 URL（避免 dataURL 撑爆产物）                                             | P2             |
| **P4**     | **多作者**：`BlogAuthor` + `BlogData.authors` + 作者页/筛选/后台管理                                     | P2             |

**通用做法（不绑定本项目）**：任何博客系统，"让别人看到"本质上只有三条路——  
① 把内容渲染成静态文件发布（Jekyll / Hugo / Hexo / Next.js SSG 都是这条路）；  
② 内容存数据库、由服务端渲染或提供 API（WordPress / Ghost / Strapi 都是这条路）；  
③ 内容托管给第三方 Headless CMS（Contentful / Sanity / 掘金 / 公众号）。  
第③条省心但受制于人，且与你"数据自己掌握"的现有取向（私有 WebDAV/飞书）冲突，故未列入候选。

### 顺带一提：微信公众号那条路

仓库里已有"发布到公众号草稿箱"（`scripts/wechat-proxy.cjs` + `useWechatPublish`）。  
它能让文章出现在公众号上，**是一次性推送、不是持续同步**，且读者在微信里看、不在你的 `/blog` 看。  
它可以作为方案 A 之外的**分发补充**（写完 → 静态站 + 公众号各发一份），但不能替代"前台对外可见"这件事。
