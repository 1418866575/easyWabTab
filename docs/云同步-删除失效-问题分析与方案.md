# 云同步「删除失效」问题分析与解决方案

> 现象：本地删除某条数据后触发云同步，该数据又被从云端重新拉取回本地，删除无效。
> 状态：**分析阶段（未实现）** · 供评审与方案拍板
> 结论一句话：**同步模型里"删除"没有对应的可同步状态，只有"缺席"；而并集式合并把"缺席"一律解释为"远端新增"，于是删除被复活。**

---

## 1. 现象与影响面

| 项 | 说明 |
|---|---|
| 现象 | 本地删除 → 同步 → 数据复现；反复删除、反复复活 |
| 触发时机 | 删除后 拉取先于推送完成；或自动推送关闭；或切换模块触发模块级拉取；或多设备互相回推 |
| 影响模块 | **除博客外几乎所有模块**（待办/笔记/日记/倒计时/健康/账本/习惯/家谱/导航/智能工作台/学生/教师/商家…） |
| 已免疫模块 | **博客（`blog`）** —— 已实现软删除墓碑，见 §3 |

## 2. 根因分析

### 2.1 根因一（核心）：合并语义是「并集」，没有删除通道

`src/composables/useCloudSync.ts:737` 的 `mergeById` 是所有信封的合并基座：

```ts
function mergeById<T>(local, remote, idKey, tsKey?) {
  const map = new Map<string, T>()
  for (const item of l) map.set(String(item[idKey]), item)   // 本地先入
  for (const item of r) {
    const id = String(item[idKey])
    const existing = map.get(id)
    if (!existing) {
      map.set(id, item)        // ←★ 远端有、本地没有 → 直接补入
    } else if (tsKey) {
      const rTs = item[tsKey]; const lTs = existing[tsKey]
      if (rNewer) map.set(id, item)   // 同 id 才比较时间戳
    }
  }
  return [...map.values()]
}
```

关键缺陷：**`!existing`（本地不存在）时无条件采用远端**。这个分支的本意是"接收另一端的新增"，但它无法区分两种"本地不存在"：

| 本地不存在的原因 | 合并应当如何处理 | 当前实际行为 |
|---|---|---|
| 另一端新增了这条 | 补入（正确） | 补入 ✅ |
| **本端刚刚删除了这条** | **保持删除** | **补入 → 复活 ❌** |

即：**"缺席"在本系统里同时表示"从未存在 / 未同步 / 已删除"三种语义，而合并逻辑只实现了第一种。** 这是删除失效的总根源。

同类逻辑在其它合并函数里重复出现，问题一致：

- `mergeStudentValue`（`useCloudSync.ts:1110`）：注释即写明"本地先入 map，**远端仅补缺失 id**"。
- `mergeFamily`（`genealogyCore.ts`）：`map.set(m.id, existing ? newer(existing, m) : m)` —— 远端独有 id 同样补入。
- `mergeBlogEnvelope` 里的 `mergeById`（`blogSyncCore.ts:18`）：也是并集，但**因为博客有墓碑才没出问题**（§3）。

### 2.2 根因二：删除是「物理移除」，删除状态无法被同步

各 store 的删除普遍是硬删：

```ts
// src/stores/workbenchTodos.ts:226
async function deleteTodo(id: string): Promise<void> {
  todos.value = toRaw(todos.value).filter(t => t.id !== id)   // ← 直接 filter 掉
}
```

家谱同理（`stores/genealogy.ts` 的 `deleteMember` 用 `filter`）。

后果：**删除这一动作没有产生任何"可被写入信封、可被对端观察到的记录"**。它只是让本地数组少了一项。于是：

- 推送成功前，云端仍持有该记录 → 任何一次拉取都会按 §2.1 把它补回来；
- 即便推送成功、云端也少了这一项，只要**另一端**还没同步过删除并先推了一次"含该项"的版本，本端拉取仍会复活。

### 2.3 根因三：时序上「拉取」天然可以抢在「推送」之前

删除后的上链路：

```
delete → persist() → markDirty()            // useCloudSync.ts:173
       → scheduleAutoPush()                 // 防抖 AUTO_PUSH_DEBOUNCE_MS = 1500ms（:182）
       → runAutoPush()                      // :217
```

而 `runAutoPush` 与拉取互斥，一旦正在 pulling 就**重新排队**（`:220`）：

```ts
if (status.value === 'pushing' || status.value === 'pulling' || status.value === 'conflict') {
  scheduleAutoPush(); return
}
```

拉取入口众多且独立触发：启动同步、定时轮询、手动同步、模块级同步（`moduleSyncCore.ts`，路由切换即触发，`MODULE_DEBOUNCE_MS = 600`）。拉取路径（`useCloudSync.ts:2202-2215`）：

```ts
const remote = result.data              // 云端信封（可能仍是删除前的旧版本）
const local  = await cfg.exportLocal()
if (cfg.signature(remote) === cfg.signature(local)) continue   // 签名相同才跳过
const merged = cfg.merge(local, remote) // ←★ 并集合并，删除项被补回
await cfg.importRemote(merged)
```

由于删除必然改变本地内容，`signature` 不相等 → 必然进入合并 → 只要云端还是旧版本，**删除必然被复活**。

更糟的边界：**若用户关闭了自动推送**（`settings.cloudSyncAutoPush !== true`，`scheduleAutoPush` 直接 return，`:205`），删除永远不会上云，此后每一次拉取都会复活它。

### 2.4 根因四：拉取侧没有"已删除"的概念可供排除

需求里提到的"拉取逻辑未排除已删除项"——**当前并不存在"已删除项"这个集合**。没有任何删除清单 / 墓碑 / 版本号可供拉取侧过滤，所以 `cfg.merge` 之后也没有 purge 步骤。这是 §2.1/§2.2 的必然结果，而非独立遗漏。

## 3. 正面范例：为什么博客不会复活

博客已经用对了方案，可直接照搬为全站规范。

**软删除（`src/stores/blog.ts:203`）** —— 不移除，改为打墓碑：

```ts
/** 软删除：写 deletedAt，从常规列表消失并进入回收站（status 不变） */
async function softDeleteArticle(id: string): Promise<boolean> {
  articles.value = toRaw(articles.value).map(a =>
    a.id === id ? { ...a, deletedAt: nowIso() } : a
  )
  await saveBlog()
}
```

**墓碑参与合并（`src/composables/blogSyncCore.ts:6`）**，注释即写明设计意图：

> 软删除（`deletedAt`）作为 tombstone 参与比较 —— 哪一侧的更新时间更晚就以哪一侧为准，因此「在 A 设备删了、B 设备还在编辑」不会把已删的文章复活。

关键在于：**被删除的记录仍然留在数组里**（带着 `deletedAt` 与更新的 `updatedAt`）。因此：

- 本地"存在墓碑" ≠ "缺席"，合并时走的是**同 id 时间戳比较**分支，而不是"远端补缺失"分支；
- 墓碑的 `updatedAt` 晚于云端那份活记录 → 墓碑胜出 → 删除状态被保留并传播到云端；
- 展示层按 `deletedAt` 过滤，回收站（`BlogTrash.vue`）可恢复（清 `deletedAt`）。

**结论：合并在"并集"框架下完全可以是正确的，前提是"删除"必须是一种可同步的状态（墓碑），而不是记录的消失。**

## 4. 解决思路总览

贯穿三条主线，对应需求的三问：

| 需求 | 思路 | 核心动作 |
|---|---|---|
| ① 如何同步本地删除状态到云端 | **删除 = 写墓碑，而不是移除** | `deleteXxx()` 改为写 `deletedAt` + 推进 `updatedAt`，记录仍留在库与信封里，随整包推送上云 |
| ② 如何让云端不再下发已删除数据 | **墓碑参与时间戳比较 + 读侧过滤 + 墓碑到期回收（GC）** | 墓碑压过云端的活记录，UI 不展示；墓碑保留期满后统一物理清除 |
| ③ 软删除 / 删除标记设计 | **统一字段与统一合并函数** | 统一 `deletedAt` 字段语义；`mergeById` 升级为 tombstone-aware，各模块一次受益 |

一条总原则：**把"删除"从「集合运算（移除元素）」改成「状态变更（写标记 + 时间戳前进）」。** 只要删除是一次带时间戳的状态变更，现有的"时间戳取新"合并策略就自动正确，无需改动合并框架的整体结构。

## 5. 详细方案设计

### 5.1 删除标记字段设计（推荐 `deletedAt`）

```ts
/** 所有参与云同步的条目统一具备的时间/删除语义 */
interface SyncableItem {
  id: string
  /** 任何变更（含删除）都必须前进 */
  updatedAt: string
  /** 墓碑：非空 = 已删除。undefined/null = 未删除（老数据兼容） */
  deletedAt?: string | null
}
```

**为什么用 `deletedAt: string | null`，而不是 `deleted: boolean`：**

| 方案 | 能否比较新旧 | 能否做回收站/恢复 | 能否多端冲突判定 | 结论 |
|---|---|---|---|---|
| `deleted: boolean` | ❌ 只有真/假，无法判断"哪端删得更晚" | ❌ 信息不足 | ❌ | 不推荐 |
| `deletedAt: string \| null` | ✅ 时间戳可比 | ✅ 记录删除时刻，可恢复 | ✅ 与 `updatedAt` 配合取新 | **推荐** |

配套约定：

1. **删除必须同时推进 `updatedAt`**，且删除时的 `updatedAt` 要严格晚于该条目任何历史版本（否则对端"刚编辑过"会盖掉删除）。
2. **读侧一律过滤** `deletedAt` 为空的项——列表、统计、派生关系（如家谱的父母/配偶引用）都要过滤，避免出现"已删成员仍出现在关系里"。
3. **恢复 = 清 `deletedAt` + 推进 `updatedAt`**（等同一次普通更新）。
4. 老数据 `deletedAt` 为 `undefined` → 视为未删除，天然兼容，无需迁移脚本。

### 5.2 同步本地删除状态到云端（主线①）

改造各 store 的删除动作，从"移除"改为"打标"：

```ts
// 改造前（硬删，删除状态无处可同步）
todos.value = toRaw(todos.value).filter(t => t.id !== id)

// 改造后（软删，删除状态随信封上云）
const now = nowIso()
todos.value = toRaw(todos.value).map(t =>
  t.id === id ? { ...t, deletedAt: now, updatedAt: now } : t
)
persist()      // 落 IndexedDB
markDirty()    // 触发防抖推送
```

要点：

- **推送是整信封 PUT**（`forcePushLocal` 导出整包上传），因此墓碑会作为信封内容的一部分传到云端，云端"知道"这条已删。
- 由于删除改变了内容，`signature` 必然变化，不会被"按签名跳过推送"的优化（`writePushedSig`）漏掉。
- **`persist()` 与 `markDirty()` 必须保留**，否则删除只停留在内存。

> ⚠️ 飞书渠道（行级镜像，无信封概念）**同样不能删行**：必须保留该行并把 `deletedAt` 写进字段更新上去。若直接删行，会重现"缺席 = 已删"的老问题。

### 5.3 让云端不再下发已删除数据（主线②）

分三层，缺一不可：

**第一层：墓碑压过活记录（阻止复活）**

升级合并函数，让墓碑参与"时间戳取新"：

```ts
/** tombstone-aware：同 id 取 updatedAt 较新者；墓碑同样参与比较，胜出则保持删除 */
function mergeByIdWithTombstone<T extends SyncableItem>(local: T[], remote: T[]): T[] {
  const map = new Map<string, T>()
  for (const item of [...local, ...remote]) {
    const prev = map.get(item.id)
    if (!prev || (item.updatedAt || '') >= (prev.updatedAt || '')) map.set(item.id, item)
  }
  return [...map.values()]
}
```

效果对照：

| 场景 | 本地 | 云端 | 合并结果 |
|---|---|---|---|
| 本端删除，云端还是旧的活记录 | 墓碑 `T2` | 活记录 `T1` | **墓碑胜（T2）→ 保持删除** ✅ |
| 他端删除，本端还在编辑 | 活记录 `T1` | 墓碑 `T2` | **墓碑胜 → 本端也删除** ✅ |
| 他端新增 | 缺席 | 活记录 | 补入 ✅（该分支仍保留） |

**第二层：读侧过滤（用户看不到已删数据）**

墓碑仍留在库里（这是必需的），但所有展示/统计入口按 `deletedAt` 过滤：

- 列表/卡片/表格：`items.filter(i => !i.deletedAt)`
- 统计、派生关系、搜索索引：同样过滤
- 删除后需清理他人对它的引用（如家谱 `parents`/`spouses` 悬空引用），且清理本身也是一次变更，要推进 `updatedAt`

**第三层：墓碑回收 GC（让云端真正不再持有）**

墓碑不能永久保留（存储膨胀 + 信封体积）。设计保留窗口：

- 墓碑保留 **N 天**（建议 30 天，可配置）后，由统一的 GC 在**所有信封推送成功后**物理清除；
- GC 前必须确认本端墓碑已上云（比对 `pushedSig` 或"上次成功推送时间 > 墓碑时间"），**未确认上云的墓碑绝不清除**，否则又会复活；
- 回收站（`BlogTrash.vue` 模式）里的"彻底删除"同样不可物理移除即了事——应标记为可 GC 的墓碑，待同步确认后再清。

> 说明：单纯"让云端把这条数据删掉"是不可靠的——在并集语义下，"云端没有"与"从未同步"无法区分，任何一端推送旧版本都会复活它。因此**必须先有墓碑，再由墓碑驱动 GC**，顺序不可颠倒。

### 5.4 统一改造方式（避免每个模块各写一遍）

1. **合并侧**：把 `useCloudSync.ts:737` 的 `mergeById` 升级为 tombstone-aware（或新增 `mergeByIdWithTombstone` 并让 `mergeTodos`/`mergeNotes`/`mergeCountdowns`/`mergeHealth`/`mergeHabits`/`mergeFamily`… 统一改调）。这样所有信封一次受益，改动面最小。
2. **删除侧**：各 store 的 `deleteXxx()` 改为软删（写 `deletedAt` + 推进 `updatedAt`）。可先做高频模块（待办、笔记、家谱、账本），再铺开。
3. **读侧**：确认列表/统计已过滤 `deletedAt`；必要时提供 `useActiveItems()` 之类的统一过滤 helper。
4. **回收站**：复用博客的 `BlogTrash.vue` 模式为其它模块提供"最近删除/恢复"，既是软删的天然产物，也降低误删成本。

### 5.5 需要一并处理的细节

| 细节 | 处理 |
|---|---|
| **时间戳单调性** | `updatedAt` 必须严格前进；时钟回拨会破坏"取新"。建议删除时用 `max(now, lastUpdatedAt + 1ms)` 保底 |
| **时间戳相等** | 需稳定的 tie-break（如比较 `id`），避免两端来回抖动 |
| **派生关系数据** | 家谱的 `parents`/`spouses`、笔记的分类引用等，删除后要清理悬空引用，且清理本身要 bump `updatedAt` |
| **飞书渠道** | 行级镜像，删除 = 更新行写 `deletedAt`，**不可删行**；`feishuPush/feishuPull` 的 force 参数与跳过优化需同步确认 |
| **推送跳过优化** | 记忆点：push 按本地签名、pull 按远端 revision 跳过；墓碑改变内容 → 签名变 → 不会被跳过（但需实测确认） |
| **老脏数据** | 已被复活的历史数据需用户重新删除一次；可提供一次性"清理"入口 |
| **云端老数据** | 无 `deletedAt` 字段 → 视为未删除，合并时正常参与比较，无需迁移 |

## 7. 验收要点

- [ ] 本地删除 → 推送 → 拉取（含强制拉取 `forcePullRemote`），数据不复活。
- [ ] 关闭自动推送时，删除仍不会在下次拉取中复活（墓碑已在本地库，拉取时墓碑压过云端活记录）。
- [ ] 多端：A 端删除、B 端同时编辑 → 合并后以较新一侧为准，语义符合预期（删除不丢失、编辑不丢失其一）。
- [ ] 恢复（清 `deletedAt`）能正常同步到对端。
- [ ] 列表/统计/派生关系均不出现已删除项。
- [ ] 纯函数（tombstone 合并 / 过滤 / 墓碑 GC 判定）有单元测试，纳入 `node --experimental-strip-types`。

## 9. 术语

- **墓碑（Tombstone）**：被删除记录留下的"已删除"占位记录（含 `deletedAt` 与更新的 `updatedAt`），用于让删除状态可参与同步与合并。
- **并集合并（Union Merge）**：当前 `mergeById` 的语义——两端 id 取并集，同 id 取时间戳较新者；远端独有 id 直接补入。
- **软删除 / 硬删除**：软删 = 打删除标记保留记录；硬删 = 物理移除记录。
- **信封（Envelope）**：云端同步文件（`workbench.json` / `blog.json` / `student.json` …），整包 PUT 上传、整包拉取后合并。
- **Lamport 逻辑时钟**：每次变更（含删除）把记录上的 `ver` +1；比较时 `ver` 优先，`ver` 相同再比时间戳，仍相同比 `clientId`。

### 本轮未做（遗留项，需单独立项）

| 项 | 原因 |
|---|---|
| 分类删除（便签 / 记账 / 待办分类） | 分类有"名称唯一性"校验，墓碑留在数组里会导致"删掉 A 分类后无法重建同名 A 分类"；要先改唯一性判定，影响面大于收益 |
| 记账账本容器（`PersonalLedger`）删除 | 账本按 `year#seq` 合并（不是按 id），且"至少保留一本""空库自动建本"逻辑耦合深 |
| 时光轴条目（嵌套在便签内） | 嵌套记录的读侧过滤点分散 |
| 飞书行级路径 | 按行删除天然不复活；墓碑是否需落行待确认 |

> ⚠️ **GC 时序约束**：`gcTombstones` 必须在本端墓碑**已成功推送上云之后**才调用，
> 否则对端仍持有活记录，本端物理清除后下一次拉取又会把它们补回来 —— 又变回复活。
