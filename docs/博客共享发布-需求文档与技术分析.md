# 博客「共享发布」需求文档与技术分析

> 基于你的思路：**自建服务同步 + 后台新增"共享"按钮 + 单篇同步到固定服务器目录 + 前台读取该目录 + 与本地去重**。
> 本文在保留你思路的前提下，修正了一个会导致**凭证泄露**的架构点，并给出可直接落地的数据模型与改造清单。

## 1. 目标与范围

| 项 | 内容 |
|---|---|
| 核心目标 | 作者在自己浏览器后台写的文章，**点一下就能让外部访客在前台看到** |
| 同步粒度 | **单篇**：后台每篇文章一个"共享"按钮，点 = 把这篇文章推到服务器目录；再点 = 取消共享（从目录移除） |
| 读取方 | 博客前台（`BlogHomeView` / `BlogPostView`）除读本地 IndexedDB 外，额外读取该服务器目录并合并去重 |
| 不在本期范围 | 多用户注册/登录、评论、阅读量统计、实时通知、草稿协作（这些是完整后端方案 B 的内容，本文仅预留接口） |

**需求映射（你之前提的三点）**：
1. 草稿/已发布控制 → 由现有 5 态状态机 + `listPublishedArticles` 已具备；本期只需"共享"动作本身限定只对**已发布**文章可用。
2. 本地/内网 → 公网可访问 → 由"服务器目录被 nginx 公开 serve"解决，无需改域名或重构。
3. 多作者前台按作者展示 → 本期在共享文件里带 `authorName`，前台即可显示；完整多作者实体（`BlogAuthor`）作为后续可选增强。

## 2. 当前数据链路（必须先认清的瓶颈）

前期已核实：文章存在**作者自己浏览器的 IndexedDB**，`blog.json` 信封经 WebDAV/飞书同步是**跨设备同步、不是发布**。前台读的是 `useBlogStore`——也就是访客**自己**浏览器的空库。

所以"访客看不到你的文章"的本质是：**数据没有离开作者的私有存储到达访客可读的地方**。"共享"动作要解决的正是这一步搬运。

好消息：渲染与过滤能力已就绪——
- `buildBlogPublic()`（`src/composables/blogStaticExport.ts:59`）：纯函数，只取**已发布且未进回收站**的文章，并把正文 `img:<id>` 还原成 **dataURL 内联**（见 `:69-70`），产出**自包含**的 HTML/Markdown。→ 每篇文章是独立的、无需额外图片同步的闭环。
- `BlogPublicPost`（`blogStaticExport.ts:18-38`）：已定义好的"对外文章"结构（title/excerpt/contentHtml/cover/分类名/标签名/作者维度字段等）。
- 前台读静态目录的范式已存在：图书模块就是 `fetch('/bookdata/manifest.json')` 读 `public/bookdata/`（`src/views/BooksView.vue:188`）。**共享目录可完全照搬这一模式。**

## 3. 总体架构（推荐实现）

```
┌──────────────┐   ① 点"共享"                          ┌──────────────────────────┐
│  作者后台 SPA  │ ── POST /api/blog-share ───────────▶ │  同源 Node 服务(16718)    │
│ (浏览器)      │    仅传文章公开子集 + id               │  · 持有服务器账号/密码    │
└──────────────┘                                       │    （服务端配置，不进bundle)│
                                                        └───────────┬──────────────┘
                                                                    │ ② 写入/删除
                                                                    ▼
                                                        ┌──────────────────────────┐
                                                        │  服务器固定目录            │
                                                        │  <webroot>/blog-share/     │
                                                        │    manifest.json          │
                                                        │    posts/<id>.json        │
                                                        └───────────┬──────────────┘
                                                                    │ ③ nginx 静态 serve（同图书）
                                                                    ▼
┌──────────────┐   ④ GET /blog-share/manifest.json      ┌──────────────────────────┐
│  访客前台 SPA │ ── fetch 同源静态文件 ───────────────▶  │  nginx 直出（无 Node 参与）│
│ (浏览器)      │    合并本地 + 共享，按 id 去重          └──────────────────────────┘
└──────────────┘
```

**为什么这样画（而不是你原话里"前端拿账号密码直接写"）：**

> ⚠️ **关键修正**：SPA 是纯静态产物，打包后 JS 对**任何访客可读**。若把服务器账号密码写进前端配置，等于把写目录的钥匙公开给全网。项目里已有正确范式——`wechat-proxy` 把 `appSecret` 落在后端 `config/wechat.env`（gitignore，仅后端可读，`nginx-easy-web-tab-site.conf:121`），浏览器只调同源 `/api/wechat`。**"共享"应同理**：
> - 账号密码 → **服务端配置**（如 `config/blog-share.env`，gitignore），由 Node 服务持有。
> - 浏览器只调**同源** `POST /api/blog-share`，**凭证永不经过浏览器**。
> - 若"服务器目录"就在部署 easy-web-tab 的同一台机器（最常见），Node 直接写本地磁盘即可，**甚至不需要账号密码**；跨机器才用 WebDAV/SFTP，且凭证只在 Node 侧。

你"写死在配置中、无需每人登录"的诉求完全保留——只是从"前端配置"挪到"后端配置"，安全性从 0 提到合理。

## 4. 数据模型

### 4.1 共享文章文件 `posts/<id>.json`
**直接复用 `BlogPublicPost`**（`blogStaticExport.ts:18-38`），不新造结构：

```ts
interface SharedArticlePost {
  id: string            // 与本地 BlogArticle.id 同键 → 去重依据
  slug: string
  title: string
  subtitle?: string
  excerpt: string
  categoryId?: string
  categoryName: string  // 已解析，访客库无分类表也能显示
  tagIds: string[]
  tagNames: string[]    // 同上
  coverKind: BlogCoverKind
  coverToken?: string
  pinned: boolean
  readingMinutes: number
  createdAt: string
  updatedAt: string
  publishedAt?: string
  contentMarkdown: string   // 图片已内联 dataURL，自包含
  contentHtml: string       // 详情页直接 v-html
  authorName: string        // 新增：本期取 settings.blogName 或"默认作者"；多作者时取 BlogAuthor.name
}
```
> 复用 `buildBlogPublic()` 的逐篇产物即可，无需导出整站 `BlogPublic`。可抽一个 `buildSharedPost(article, blog, renderHtml)` 包装它。

### 4.2 清单 `manifest.json`
仿 `BookManifestItem`，前端先拉清单再按需拉正文：

```ts
interface BlogShareManifest {
  generatedAt: string
  count: number
  posts: Array<{
    id: string
    slug: string
    title: string
    excerpt: string
    authorName: string
    categoryName: string
    updatedAt: string
    size: number            // 字节，便于前端估算
  }>
}
```

### 4.3 不引入新数据库
"共享库"= 文件系统：`manifest.json` + `posts/*.json`。清单即索引，nginx 直接静态托管，零新增中间件。与图书 `public/bookdata/` 完全一致。

## 5. 同步流程（共享 / 取消共享）

| 步骤 | 动作 | 注意点 |
|---|---|---|
| 共享（upsert） | 后台点"共享" → 客户端组装 `SharedArticlePost`（用 `buildSharedPost`）→ `POST /api/blog-share` | 仅当 `status==='published' && !deletedAt` 才允许；否则按钮禁用并提示"仅已发布文章可共享" |
| 服务端写 | Node 收到后：**先写临时文件 `posts/<id>.tmp` → rename 为 `<id>.json`**（原子替换，避免读到半截） | 防并发读脏数据 |
| 更新清单 | 重写 `manifest.json`（同样 tmp+rename，或加文件锁） | 清单是单点，必须原子 |
| 取消共享 | 点"取消共享" → `DELETE /api/blog-share/:id` → 删 `posts/<id>.json` + 从清单移除 | 幂等：文件不存在也返回成功 |
| 失败处理 | 网络/服务端错 → 前端 toast 报错，**不本地标记"已共享"**；成功响应后才把 `sharedAt` 写入本地文章元数据 | 避免"以为共享了其实没共享" |
| 幂等 | 同 id 重复 POST = 覆盖；`updatedAt` 用于前台去重判新旧 | — |

**本地需新增字段**（挂在 `BlogArticle` 或单独的本地元数据）：`sharedAt?: string`（最近一次成功共享时间），用于后台显示"已共享/未共享"状态和按钮文案切换。

## 6. 去重与合并（前台核心逻辑）

前台列表 = 合并 **本地 IndexedDB 文章** + **共享目录文章**，按 `id` 去重：

```ts
function mergeArticles(local: BlogArticle[], shared: SharedArticlePost[]): DisplayArticle[] {
  const map = new Map<string, DisplayArticle>()
  for (const a of local) map.set(a.id, { ...toDisplay(a), source: 'local' })
  for (const s of shared) {
    const ex = map.get(s.id)
    // 同 id：取 updatedAt 较新者；相等则本地优先（作者本机为权威）
    if (!ex || s.updatedAt > ex.updatedAt) map.set(s.id, { ...toDisplay(s), source: 'shared' })
  }
  // 可见性：仅已发布且未删除（访客看不到草稿；作者本机草稿也不在前台出现）
  return [...map.values()].filter(a => a.status === 'published' && !a.deletedAt)
}
```

要点：
- **作者本机**既有本地副本又有共享副本 → 同 id 只显示一条（去重生效）。
- **访客**本地库为空 → 只剩共享文章，自然全展示。
- 可在卡片上加"来源"小标（`本地`/`共享`），纯展示，非必须。

## 10. 安全分析（务必看）

1. **凭证绝不进前端 bundle**（最重要）：写死在**后端** `config/blog-share.env`，复用 `wechat-proxy` 的 gitignore+仅后端可读模式。前端只调同源 API。
2. **共享文件不泄露信封**：只写 `SharedArticlePost`（公开子集）。**绝不可**把 `blog.json` 信封或 `BlogData` 整体下发——信封含草稿、回收站、以及其他可能写入的明文凭证（如 `wechat.appSecret`）。逐篇公开子集从结构上杜绝了这一泄漏。
3. **写接口防护**：`POST/DELETE /api/blog-share` 具备写文件能力。在公开部署下若不做防护，任何人都能注入/删除文章。建议（按成本递增）：
   - 基础：nginx 对 `/api/blog-share` 的写方法加 **IP 白名单**（仅作者出口 IP）；
   - 进阶：Node 侧校验一个**服务端 `BLOG_SHARE_WRITE_TOKEN`**（同样只后端持有；浏览器不传，改由"作者后台在同源会话下调用"——但 SPA 无会话，故更现实的是配合 IP 白名单 + 非公开部署）。
   - 本质：你这套是**单作者 / 内网可信**模型，网络层隔离是相称的控制；若要做成"公网多作者可写"，那就回到方案 B（完整后端+账号体系），与本次诉求相悖。
4. **目录权限**：`blog-share/` 仅 Node 进程可写（如 `0o750`），nginx（www-data）只读；禁止该目录可写被公开利用。
5. **清单原子写**：`manifest.json` 是单点索引，必须 tmp+rename 或加锁，避免并发读到损坏清单导致前台整页崩。

## 13. 实施路线（已落地）

- **P0 设计确认**：6 项决策已确认（§12）。
- **P1 服务端**：`config/blog-share.env` 配置加载 + `POST/DELETE /api/blog-share` 端点 + 写 `<webroot>/blog-share/`（原子写 `tmp+rename` + 清单维护 + `blogShareWithinDir` 目录越界防护）。已通过 curl 冒烟测试（Windows）。
- **P2 后台共享按钮**：`useBlogShare()` + 列表/编辑器按钮 + `sharedAt` 经 `store.updateArticle` 落盘并触发云同步（跨设备保留已共享态）+ 禁用条件 + toast。
- **P3 前台读取合并**：`useBlogShared()` 拉清单、合并去重（`mergeArticlesForListing`）、`BlogHomeView`/`BlogPostView` 加载/错误态；详情页本地不可见时按 slug 从共享目录兜底。
- **P4 打磨**：来源标记（`.ba-shared` 蓝底）、作者名显示、分页/筛选复用现有 `useViewMode`/卡片组件、nginx `alias` 生产直出 + vite 转发 dev/preview。
- **P5（可选）**：多作者 `BlogAuthor` 实体、阅读量/评论（此时再评估是否升级到方案 B）。

### 实现中修复的两个服务端 bug（Windows 部署关键）
1. `blogShareWithinDir` 越界防护原先用 `path.join` 比对导致分隔符混用（前端 `/` vs `path.sep` `\`），Windows 上误判越界使 POST/GET 全部失败 → 改用 `path.resolve` 统一两端再比对。
2. POST/DELETE 原把文章文件写到 `<dir>/<id>.json`，但前端读取路径与 nginx alias 均为 `posts/<id>.json` → 改为统一写入/删除 `posts/` 子目录，并 `mkdir(path.dirname(file), {recursive:true})` 建父目录。
3. `blogShareWithinDir` 不再套用严格 ID 正则（文件名带 `.`/`posts/` 子路径），ID 合法性由各调用点已做正则校验；越界防护完全由 `path.resolve`  containment 负责。

## 14. 推荐结论

**采用你的"单篇共享到固定目录 + 前台读取去重"思路，但把凭证从前端配置改到后端配置（复用 wechat-proxy 范式）。** 理由：

1. 你最难的部分（`buildBlogPublic` 的自包含渲染 + 图片内联）**已经写好**，本期只是"写单篇文件 + 前台换数据源"。
2. 复用图书 `fetch('/bookdata/manifest.json')` 范式，前台读取**零新中间件**，nginx 已能静态托管。
3. 凭证后端化后，安全从"全网可见"提升到"相称于内网单作者"，且不增加任何运维负担。
4. 文件系统即数据库、按 id 去重合并，逻辑清晰、易测试、易回滚（删文件即下架）。
5. 预留了 `authorName` 与后续多作者/后端升级的接口，不锁死架构。

**最大风险**是"前端写死凭证"这一原始表述——只要改成后端配置，整条链路就是安全且可落地的。
